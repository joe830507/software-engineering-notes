# AWS 總覽、全球基礎設施與認證地圖

> 內容整理自個人的 SAA-C03 與 AIF-C01 學習筆記，並對照 AWS 官方文件查證與更新（來源列在頁尾）。
> 服務的數字（配額、折扣、可用區域）會隨時間調整，**正式設計前請以官方文件與 Service Quotas 主控台為準**。

## 學習地圖

AWS 服務上百個，但可以收斂成「身分、網路、運算、儲存、資料庫、整合、維運、成本、AI」九個問題域。每個問題域在筆記裡對應一到兩頁，最後有一頁彙整易混淆的比較與情境關鍵字。

| 問題域 | 要回答的問題 | 頁面 |
| --- | --- | --- |
| 身分與權限 | 誰能對哪個資源做什麼？多帳號怎麼管？ | IAM、Organizations 與身分整合 |
| 資料保護與偵測 | 資料怎麼加密？怎麼知道被入侵？ | 加密、機密與偵測 |
| 網路 | 流量怎麼進、怎麼出、怎麼互連？ | VPC 與網路連線、DNS、負載平衡與邊緣 |
| 運算 | 程式跑在哪裡？ | 運算 |
| 儲存 | 資料放哪裡、多快、多貴？ | 儲存 |
| 資料庫 | 選哪種資料庫、怎麼備援？ | 資料庫 |
| 整合與分析 | 服務之間怎麼解耦？資料怎麼分析？ | 整合與分析 |
| 韌性與成本 | 壞掉怎麼辦？怎麼省錢？ | 韌性與災難復原、成本與維運 |
| 生成式 AI | 怎麼用 Bedrock 建應用、怎麼負責任地用？ | 生成式 AI 兩頁 |

### 建議閱讀順序

| 階段 | 頁面 | 目標 |
| --- | --- | --- |
| 1. 打底 | 本頁、IAM | 看得懂 Region／AZ、共同責任、權限評估 |
| 2. 基礎建設 | VPC、運算、儲存、資料庫 | 能為工作負載選對元件 |
| 3. 架構品質 | 整合與分析、韌性、成本與維運 | 能回答「壞了怎麼辦、貴了怎麼辦」 |
| 4. 延伸 | 生成式 AI、速查表 | 補 AI 服務與考前複習 |

## 全球基礎設施

| 概念 | 說明 | 設計上的意義 |
| --- | --- | --- |
| Region | 地理上獨立的區域，彼此資料與資源互相隔離 | 選擇時考量法規落地、延遲、服務可用性與價格 |
| Availability Zone（AZ） | Region 內一個或多個獨立機房，彼此有獨立電力與網路，以低延遲連線 | 高可用的基本單位；撐過機房故障就要跨 AZ |
| Edge Location | CloudFront、Route 53 等服務的邊緣節點 | 把內容或 DNS 解析放到離使用者近的地方 |
| Local Zones、Wavelength、Outposts | 把 AWS 延伸到都會區、電信 5G 邊緣、自家機房 | 超低延遲、資料必須留在本地的情境 |

### 各資源的作用範圍

判斷「要不要自己做跨 AZ」的第一步，是知道資源本身落在哪一層。

| 資源 | 範圍 | 高可用做法 |
| --- | --- | --- |
| Subnet、EBS、Zonal NAT Gateway | 單一 AZ | 跨 AZ 部署需分別配置；EBS 靠快照跨 AZ 或跨 Region |
| Regional NAT Gateway | Region，可涵蓋多個 AZ | 自動模式隨工作負載擴展；模式與限制見「VPC 與網路連線」 |
| EC2 | 單一 AZ | Auto Scaling Group 跨多個 AZ，前面放 ELB |
| ELB、EFS、S3、DynamoDB | Region（跨多個 AZ） | S3 與 DynamoDB 內建；ELB 要自行啟用多個 AZ 的子網路；S3 與 EFS 的 One Zone 類別只在單一 AZ |
| RDS | 單一 AZ | 開啟 Multi-AZ |
| Route 53、CloudFront、IAM、Global Accelerator | 全球 | 內建 |

## 共同責任模型

| 責任方 | 負責什麼 | 例子 |
| --- | --- | --- |
| AWS | 雲端**本身**的安全：實體設施、硬體、受管服務的基礎設施 | 資料中心門禁、EC2 虛擬化層、S3 內部副本 |
| 客戶 | 雲端**裡面**的安全：資料、存取權限、組態、應用程式 | IAM 權限、Security Group 規則、是否開加密、作業系統修補（EC2） |

責任邊界隨服務型態移動：用 EC2（IaaS）要自己修補作業系統；用 RDS 由 AWS 修補資料庫引擎，但帳號權限與資料仍是客戶的責任；用 Lambda 連執行環境都由 AWS 管。**越是全受管的服務，客戶要負責的越少，但資料與權限永遠是客戶的。**

## Well-Architected Framework 六大支柱

AWS 用六個支柱檢視一個架構是否良好；各支柱的設計目標彼此會有取捨（例如更高的可靠性通常增加成本）。

| 支柱 | 核心問題 | 本筆記對應頁面 |
| --- | --- | --- |
| 卓越營運 | 怎麼監控、自動化並持續改進？ | 成本與維運 |
| 安全 | 怎麼保護資料、系統與資產？ | IAM、加密與偵測、VPC |
| 可靠性 | 故障時能否自動復原、滿足需求量？ | 韌性與災難復原、資料庫 |
| 效能效率 | 怎麼有效使用運算資源並隨需求演進？ | 運算、儲存、DNS 與邊緣 |
| 成本最佳化 | 怎麼避免不必要的支出？ | 成本與維運 |
| 永續性 | 怎麼降低工作負載的環境衝擊？ | 夠用就好的規格、無伺服器 |

Well-Architected Tool 可以依這個框架對工作負載做自我審視。

## 認證路線與作答原則

| 項目 | SAA-C03（Solutions Architect Associate） | AIF-C01（AI Practitioner） |
| --- | --- | --- |
| 層級 | 助理級，考「設計與選型」 | 基礎級，考「看得懂、會選擇」 |
| 題數與時間 | 65 題（50 題計分）、130 分鐘 | 65 題（50 題計分）、90 分鐘 |
| 通過門檻 | 720／1000 | 700／1000（總分制） |
| 範疇配分 | 安全 30%、韌性 26%、高效能 24%、成本 20% | AI/ML 基礎 20%、GenAI 基礎 24%、FM 應用 28%、負責任 AI 14%、安全與治理 14% |

作答原則（兩張證照共通）：

1. **只根據題目寫出的條件判斷**，不自行補上題目沒提的需求（沒說全球使用者，就不要拿「全球分佈」當理由）。
2. 先分清楚題目要的是高可用（撐過 AZ 故障）、災難復原（撐過 Region 故障）還是解耦（撐過下游變慢），三者答案不同。
3. 「最少營運負擔」優先選受管或無伺服器；「最具成本效益」要在**滿足所有限制**後挑最便宜的。
4. 選項都能達成需求時，用題目的限定詞（最快、最省、不改程式）排除。
