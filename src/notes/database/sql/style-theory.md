# SQL 寫法風格與關聯模型理論

## 加速的寫法

> 以下是「只改 SQL 寫法」就可能奏效的招式，與 DBMS 無關。**一切以執行計畫與實測為準**，新版最佳化器常會自動改寫。完整流程見〈效能最佳化〉。

### 效能心法

- 最大的瓶頸通常是**存取慢速儲存**（硬碟、網路）。所以多數技巧是：**減少排序、善用索引、減少中介表**。
- 趁早用條件減少列數：「早還債，不滾雪球」。

### 選擇有效率的搜尋

```sql
-- 子查詢型 IN → EXISTS（有索引時可直接查索引，找到一筆就停）
SELECT * FROM customers c
WHERE  EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
```

- `IN` 的參數是常數清單時不用改。
- 改成連結（扁平化）可能產生重複列，需要 `DISTINCT`，此時 `EXISTS` 更好。

### 避開偷偷發生的排序

會觸發排序（或雜湊）的運算：`GROUP BY`、`ORDER BY`、彙總函數、`DISTINCT`、`UNION`/`INTERSECT`/`EXCEPT`、視窗函數。記憶體排不下就用硬碟，效能大跌。

| 招式 | 說明 |
|---|---|
| `UNION` → `UNION ALL` | 確定沒有重複就不要去重 |
| `DISTINCT` → `EXISTS` | 一對多連結產生的重複，用半結合避免 |
| `MAX`/`MIN` 用在有索引的欄位 | 只看索引末端 |
| 條件從 `HAVING` 搬到 `WHERE` | 先過濾再彙整，且 `WHERE` 能用索引 |
| `GROUP BY`/`ORDER BY` 欄位有索引 | 部分系統可跳過排序 |

```sql
-- 對分組鍵篩選，最佳化器可能自動下推
SELECT order_date, SUM(qty) FROM orders GROUP BY order_date HAVING order_date = DATE '2026-10-01';
-- 明確先篩選，不保證比上一式更快
SELECT order_date, SUM(qty) FROM orders WHERE order_date = DATE '2026-10-01' GROUP BY order_date;
```

只有針對**彙總結果**的條件（`SUM(qty) > 100`）才放 `HAVING`。

### 索引失效：「欄位要乾淨」

| 寫法 | 問題 / 改法 |
|---|---|
| `WHERE col * 1.1 > 100` | 把運算移到常數端：`col > 100 / 1.1` |
| `WHERE SUBSTR(col, 1, 1) = 'a'` | 改 `col LIKE 'a%'` |
| `WHERE str_col = 10` | 隱含轉換，改 `'10'`；轉換要加在**常數**那一側 |
| `IS NULL` / `IS NOT NULL` | MySQL / PostgreSQL 的 B-tree 可索引 NULL；依資料庫實作判斷 |
| `<>`、`NOT IN` | 否定形通常用不到索引 |
| `OR` | 可評估拆分，但分支須互斥，否則會新增重複列 |
| `LIKE '%abc'` | 非前方一致 |
| 複合索引缺首欄 | 最左前綴原則 |

函式索引（表達式索引）可以讓左側有函數，但維護麻煩，不要濫用。

### 減少中介表

- 用 `HAVING` 代替「子查詢 + `WHERE`」：不要為了篩選彙總結果多包一層。
- 多個 key 的 `IN`：用資料列比較 `(a, b) IN (SELECT a, b ...)`，不要串接成字串（欄位不乾淨）。
- **依結果粒度決定是否先彙整再連結，避免重複加總**。
- 視圖含彙整或集合運算時，使用前要有計畫；必要時用實體化視圖。

### 其他提醒

- `SELECT *` 不建議。
- 時間範圍用 `>=` 加 `<`，不要對欄位包 `DATE()`。
- 深度分頁用 keyset 或延遲關聯，不要大 `OFFSET`。

## 撰寫風格

### 資料表與欄位設計

- 名稱要有意義：用完整單字，英文名詞，不用 `data1`、`tmp`、`col_a`。
- 命名只用英數字與底線；表名單／複數團隊統一。
- **一個欄位 = 一種屬性**：不要把多個資訊塞在一個欄位（`'M-1990-TW'`），也不要依位置呼叫（`col1`、`col2`…`col12`）。
- 用 `NOT NULL` + 預設值減少 NULL；代碼欄用字串。

### 寫法規範

```sql
SELECT   e.emp_id
       , e.name
       , d.dept_name
FROM     employee   e
JOIN     department d ON d.dept_id = e.dept_id
WHERE    e.active = 1
  AND    e.hire_date >= DATE '2020-01-01'
ORDER BY e.emp_id;
```

- 關鍵字大寫、名稱小寫，一個子句一行，縮排一致。
- 逗號放行首或行尾沒有標準答案，**團隊一致即可**（行首逗號方便增刪與 diff）。
- **不用 `SELECT *`、不用 `ORDER BY 2`**（欄位位置）。
- 註解說明「為什麼」，不是「做什麼」。

### 學標準語，少用方言

- 優先用標準 SQL：`CASE`（不用 `DECODE`、`IF`）、`COALESCE`（不用 `NVL`、`IFNULL`）、`CURRENT_TIMESTAMP`、`JOIN ... ON`。
- 外連結**只用 `LEFT`**（`RIGHT` 都能改寫成 LEFT），不要用 Oracle 的 `(+)`。
- 方言要用就集中、加註解，方便日後移植。

### 驅逐關聯子查詢，從 FROM 開始寫

- 關聯子查詢難讀、可能慢，優先改成 JOIN、視窗函數、或先彙整的衍生表。
- 寫查詢的順序：**先寫 `FROM`（要用哪些表、怎麼連），再寫 `WHERE`，最後才決定 `SELECT`**。執行順序也是這樣，思路比較順。

### 可讀性優先於效能

先寫清楚，量到有瓶頸再最佳化；寫得再快，團隊讀不懂就是維護成本。

## 關聯模型理論

### 關聯式資料庫簡史

- 之前是**階層式**（IMS）與**網路式**（CODASYL）資料庫：程式要自己沿著指標走，資料結構一改程式就壞。
- 1970 年 **Codd** 提出關聯模型；起初效能被認為太差、學術味太重（**破壞性創新**：先從低階市場切入，之後逐步取代）。
- RDB 勝出的原因：站在**使用者角度**（不用知道資料怎麼存），查詢語言簡單。
- 現代課題：①效能與一致性的折衷（分散式、CAP）；②資料模型的極限（巢狀、圖形、文件）。**NoSQL** 補足後者，但沒有取代 RDB。

### 關聯 ≠ 表格

- **關聯（relation）**是數學上的集合：一組同型的元組（tuple）。**表格**只是它的一種呈現。
- 關聯的欄位屬於某個**定義域（domain，型別）**。SQL 的 `CREATE DOMAIN` 就是自訂定義域（MySQL 不支援）。
- **關聯值**（某時刻的內容）vs **關聯變數**（存放關聯值的容器，即 `CREATE TABLE` 的表）。
- 關聯內的元組**不重複、沒有順序**；SQL 的表允許重複列與 NULL，是對模型的偏離。

### 封閉性與代數

- **封閉性（closure）**：關聯運算的輸入與輸出都是關聯，所以可以無限串接。這使得**子查詢、View、CTE** 成為可能。
- 類比：UNIX 管線，每個指令的輸入輸出都是文字流，所以能組合。
- 嚴謹的代數結構（群、環、體）讓最佳化器能安全地**改寫**查詢而不改變結果。

### 擺脫位址

- 關聯模型的核心主張：「我們要的是資料，不是資料的位址。」用**內容**（key）找資料，而不是指標或陣列索引。
- 程式語言裡的變數本質是「位址的化身」，是 bug 的溫床（別名、副作用）。函數型語言延續這個方向。
- 這也是為什麼 SQL 不要依賴 `ROWNUM`、物理順序、自增 ID 的連續性。

### 順序、分組與遞迴

- **順序**：Codd 原本只說列沒有「有意義的」順序；後繼者更強硬地否定順序。視窗函數是在不破壞集合概念下臨時賦予順序。
- **GROUP BY / PARTITION BY**：把集合切成互不重疊、聯集為全體的「**類**」（等價類）。取模運算（剩餘類）可用來做大致均勻的抽樣。
- **遞迴集合**：自然數可以用集合定義（0 = ∅，n+1 = n ∪ {n}），每一圈包含前一圈。自我連結算排名、遞迴 CTE 都是這個概念。

### 三值邏輯的歷史

- 三值邏輯由盧卡西維茨在 1920 年代提出，批判古典邏輯的排中律（「神的邏輯」：事實只有真或假）。
- 資料庫需要處理「未知」，所以引入 unknown；代價是排中律不再成立、查詢結果出現反直覺的行為。這是 NULL 帶來的理論成本。

## 面試速查

**Q：怎麼讓一個慢查詢變快？**
1. 看執行計畫（`EXPLAIN`）找瓶頸。2. 確認條件欄位是否「乾淨」能用索引。3. 減少回傳列與欄。4. 子查詢 `IN` 改 `EXISTS`、`HAVING` 條件搬 `WHERE`、`UNION` 改 `UNION ALL`。5. 深分頁用 keyset。6. 最後才考慮調整索引或表結構。

**Q：為什麼說 SQL 是宣告式語言？**
只描述要的結果，不描述步驟。最佳化器根據統計資訊與索引決定執行計畫，所以同一個語句可能在資料量變化後換計畫。

**Q：為什麼不推薦 `NATURAL JOIN`、`SELECT *`、`ORDER BY 2`？**
都依賴「隱含」或「位置」：欄位改名、新增欄位、調整順序時悄悄壞掉。顯式比隱式安全。

**Q：NULL 該不該使用？**
依業務語意決定；未知不等於零。使用 NULL 時明確處理三值邏輯、聚合與排序。
