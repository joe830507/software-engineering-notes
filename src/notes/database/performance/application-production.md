# 應用層調校與上線

## Spring Boot / JPA 專項

SQL 本身沒問題、資料庫卻很慢時，要回頭看應用層：

- **N+1**：觀察 Hibernate SQL 日誌或統計資訊；視需求使用 `JOIN FETCH`、`@EntityGraph`、批次載入（Batch Fetching）或 DTO Projection。
- **避免無界集合載入**：大量資料改用分頁、串流或批次處理；注意交易與連線生命週期。
- **連線池（Connection Pool）**：監控 HikariCP 的 active、idle、pending 與 acquisition time；**不要只靠調大 pool 解決慢 SQL**，這可能加重 DB 負載。
- **交易（Transaction）**：縮短交易時間，避免在持有鎖時執行外部 API 或耗時工作。
- **批次操作（Batching）**：大量寫入時評估 JDBC batching 與合理批次大小。
- **快取（Caching）**：僅在資料一致性、失效策略與命中率可控時採用；先避免錯誤的 SQL 與資料存取模式。

### N+1 與 Nested Loop 的差別

- **N+1**：應用程式（ORM）先查一次集合，再為每個元素**額外發出一支 SQL**。
- **Nested Loop**：**同一支 SQL** 內，資料庫以外層每一列去呼叫內層查找，累計次數可能很高。

兩者症狀相似（單次很快、總量很大），但修法不同：前者修應用程式的載入策略，後者看 SQL 與索引、是否真的需要那麼多列。

## 上線前檢查清單

- [ ] 確認 SQL 結果與原查詢一致（含 NULL、排序、時區、重複列與分頁邊界）。
- [ ] 留存優化前後執行計畫與測試數據。
- [ ] 測試代表性的熱門值、冷門值、極端值及不同資料分布。
- [ ] 檢查新增索引對寫入延遲、儲存空間與建索引鎖定 / 資源的影響。
- [ ] 確認 schema migration、部署時機及回滾方式。
- [ ] 上線後監控 P95 / P99、QPS、CPU、I/O、鎖等待與錯誤率。

大表加索引要用 Online DDL 或 `CREATE INDEX CONCURRENTLY`，並在離峰時段執行、監控主從複製延遲。細節見「索引設計」頁的「大表事後加索引」。

## 面試回答的準備

這個主題的面試問題多半是開放題。回答的骨架：

1. **先量測**：用 APM、slow query log、`pg_stat_statements` 找出**總耗時**最高的 SQL（單次耗時 × 次數）。
2. **看執行計畫**：`EXPLAIN ANALYZE`，看掃描列數、預估與實際差距、排序、JOIN、`loops`。
3. **對症處理**：缺索引 / 索引失效、SQL 寫法（函式包欄位、深分頁、`SELECT *`）、統計資訊過時、N+1、鎖與連線池。
4. **驗證與代價**：比較 P95、資源使用、寫入影響與正確性，並持續監控。

要避免的說法：

- 「超過多少筆就要加索引」。
- 「加大連線池就會變快」。
- 「看到全表掃描就一定要改」。
- 「cost 越低就越快」。

這些都是上一頁整理過的常見誤區。
