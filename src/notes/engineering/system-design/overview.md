# 系統設計總覽與面試框架

> 內容依據三本書整理：《內行人才知道的系統設計面試指南》（Alex Xu）、《Clean Architecture 無瑕的程式碼：整潔的軟體設計與架構篇》（Robert C. Martin）、《軟體架構原理：工程方法》（Mark Richards、Neal Ford）。
> 書中的流量、儲存空間數字都是面試練習用的**假設值**，不是真實系統的統計。

## 學習地圖

系統設計有兩個層次，三本書各負責一部分：

| 層次 | 要回答的問題 | 對應來源 | 本章頁面 |
| --- | --- | --- | --- |
| **系統規模設計** | 使用者變多、資料變大時，系統怎麼切、怎麼擴展？ | 系統設計面試指南 | 擴展與估算、基礎元件、三個案例頁 |

## 面試四步驟

來源書提出的框架。系統設計面試模擬的是**兩位同事針對模糊問題一起找出方案**的過程，沒有標準答案，過程比最後的圖更重要。

| 步驟 | 建議時間（45 分鐘面試） | 做什麼 |
| --- | --- | --- |
| 1. 了解問題、確立範圍 | 3–10 分鐘 | 問清楚功能、規模、限制，把假設寫下來 |
| 2. 提出高階設計、取得認可 | 10–15 分鐘 | 畫方框圖、做粗略估算、用具體情境走一遍 |
| 3. 深入設計 | 10–25 分鐘 | 和面試官確認要深入的元件，先深入最關鍵的 |
| 4. 匯整總結 | 3–5 分鐘 | 說明瓶頸、故障情境、監控、下一個規模階段 |

時間只是粗略參考，實際依問題範圍與面試官要求調整。

### 第 1 步：該問什麼

不要像搶答的學生一樣直接給答案。書中列的問題方向：

- 要做哪些特定功能？產品有多少使用者？
- 公司預計多快擴大規模？3 個月、6 個月、一年後？
- 有哪些技術強項、現有服務可以利用？

以「設計動態訊息系統」為例，書中的澄清問題有：行動 App 還是 Web？最重要的功能？排序是時間倒序還是加權？一個使用者有幾個朋友？流量多少？有沒有圖片、影片？

### 第 2 步：高階設計

- 和面試官像團隊合作一樣，一起畫出初始藍圖。
- 用方框圖標出客戶端、API、Web 伺服器、資料儲存、快取、CDN、訊息佇列等。
- 用粗略估算確認設計符合規模；若估算要花很多時間，先向面試官說明。
- 用具體使用範例從頭走一遍，常能發現漏掉的邊界情況。
- 是否要列 API 與資料表，取決於題目：設計「Google 搜尋」太細，設計「多人撲克後端」則合適。

### 第 3 步：深入設計

- 和面試官確定要深入的元件。短網址通常深入雜湊函式，聊天系統則是延遲與上線狀態。
- 避免卡在細節。書中舉例：詳細討論 Facebook 動態訊息的 EdgeRank 演算法，無法證明你能設計系統。

### 第 4 步：匯整總結

可以主動談的方向：

- 找出系統瓶頸並討論改進，不要說設計「已經完美」。
- 重新回顧設計，尤其當你提出過多個方案時。
- 故障情境：伺服器掛掉、網路斷線。
- 營運面：怎麼監控指標與錯誤日誌、怎麼逐步上線。
- 規模曲線的下一步：支援 100 萬使用者的設計，要支援 1,000 萬時要改什麼？

### 應該做與不該做

| 應該做 | 不該做 |
| --- | --- |
| 為了釐清而提問，不要假設自己的假設一定對 | 沒準備就面對典型題目 |
| 了解問題的真正需求 | 需求和假設還沒清楚就跳進解法 |
| 沒有最佳答案：新創與百萬使用者公司的解法本來就不同 | 一開始就在單一元件上鑽太細 |
| 把想法說出來，像隊友一樣溝通 | 卡住時不求提示、只顧自己默默想 |
| 能提出多種做法就提出並比較 | 設計完就當面試結束，不再要回饋 |

## 把三本書串起來的主軸

三本書談的尺度不同，但有三個共通想法，答題與寫設計文件時都用得上：

| 主軸 | 在三本書中的樣子 |
| --- | --- |
| **一切都是取捨** | 面試指南：一致性 vs 可用性、推 vs 拉扇出、301 vs 302。《軟體架構原理》第一法則：「軟體架構的一切皆是取捨」，並強調「為什麼」比「如何」重要。 |
| **把變動隔離** | Clean Architecture：高階政策不依賴低階細節，用邊界隔開。面試指南：訊息佇列、無狀態 Web 層讓元件能各自擴展。 |
| **先釐清真正重要的特性** | 面試指南：規模與非功能需求先確認。《軟體架構原理》：架構特性要挑「少數」真正重要的，每多一項就增加設計複雜度。 |

### 回答範本

一題的回答可以用同一條線串起來：

> 需求與規模 → 估算（QPS、儲存） → 高階元件與資料流 → 挑一兩個關鍵元件深入 → 取捨與替代方案 → 故障、監控、下一步擴展

例：「短網址每天 1 億筆寫入，約 1,160 QPS，讀寫比 10:1，所以讀取約 11,600 QPS，要放快取。短碼我用 62 進位轉換唯一 ID，優點是不會衝突，缺點是序號可預測，需要搭配限流與存取控制。」
