# Clean Architecture（二）：元件、邊界與整潔架構

> 對應《Clean Architecture》Part IV–VII（第 12–34 章）。SOLID 管的是類別與模組，這一頁往上談**元件**（可獨立部署的單位），再談**邊界**與整潔架構的同心圓。

## 元件原則

**元件**是可獨立部署的最小單位：Java 的 jar、.NET 的 DLL、Ruby 的 gem 等。元件原則回答兩個問題：哪些類別該放同一個元件（內聚）、元件之間該怎麼依賴（耦合）。

### 元件內聚：三個原則

| 原則 | 全名 | 意思 | 對應 |
| --- | --- | --- | --- |
| **REP** | 重用／發佈等價原則 | 重用的粒度就是發佈的粒度；元件要有版本號與發佈記錄，使用者才能決定何時升級 | — |
| **CCP** | 共同封閉原則 | 因**相同理由、同時變更**的類別放在同一個元件；為同一個元件找出同一種變更理由 | 元件版的 **SRP** |
| **CRP** | 共同重用原則 | 不要強迫元件使用者依賴他們不需要的東西；**會一起被重用的類別**才放在一起 | 元件版的 **ISP** |

這三者互相拉扯：**REP 與 CCP 是包容性原則**，傾向把共同發佈或共同變更的類別放在一起，使元件變大；**CRP 是排除性原則**，避免使用者依賴不需要的類別，使元件變小。專案早期偏向 CCP（開發容易），成熟後逐漸重視 REP（重用）。

### 元件耦合：三個原則

**ADP：無環依賴原則。** 元件依賴關係圖**不可以有環**。有環會造成「隔天早上症候群」（morning-after syndrome）：你下班前程式能跑，隔天卻因為別人改了你依賴的東西而壞掉。用「每週建置」的做法有時能緩解，但專案越大問題越嚴重。打破環的兩種方式：

1. 用 **DIP**：在環中插入一個介面，讓其中一條依賴反向。
2. 建立一個**新元件**，讓互相依賴的兩者都依賴它。

依賴結構不是由上而下設計，而是隨專案演進、**由下而上**長出來的，所以要持續監控並重構。

**SDP：穩定依賴原則。** 依賴的方向要朝向**更穩定**的元件。穩定度用不穩定性指標衡量：

```text
Fan-in  ：依賴「它」的外部類別數（輸入依賴）
Fan-out ：「它」依賴的外部類別數（輸出依賴）

不穩定性 I = Fan-out / (Fan-in + Fan-out)      範圍 0 ~ 1
  I = 0：很穩定（沒有輸出依賴，很多人依賴它，不容易改動）
  I = 1：很不穩定（依賴別人、沒人依賴它，容易改動）
```

並非所有元件都該穩定：如果每個元件都極度穩定，系統就改不動。要讓**容易變更的元件不穩定**，穩定的元件才是被依賴的對象。

**SAP：穩定抽象原則。** 元件的抽象程度要與它的穩定度一致：

```text
抽象度 A = 元件中抽象類別（介面、抽象類）的數量 / 類別總數      範圍 0 ~ 1
```

穩定的元件應該很抽象（才能被擴充而不用修改）；不穩定的元件應該很具體。把每個元件畫在以 `I`（橫軸）與 `A`（縱軸）為座標的圖上：

| 區域 | 說明 |
| --- | --- |
| **主序列**（連接 (0,1) 與 (1,0) 的線） | 穩定又抽象、或不穩定又具體——理想位置 |
| **痛苦區**（左下，I 低、A 低） | 穩定但具體：很多人依賴又難以擴充，例如資料庫 schema |
| **無用區**（右上，I 高、A 高） | 抽象卻沒人依賴 |

與主序列的距離：

```text
D = |A + I − 1|        D 越接近 0 越好
```

可用來量測各元件，找出要重構的目標。

## 什麼是架構

### 架構的目的

> 軟體架構的目的是**支援系統的生命週期**：容易理解、開發、維護、部署。策略是**盡可能長時間保持更多選項是開放的**。

| 面向 | 說明 |
| --- | --- |
| 開發 | 團隊結構會影響架構（Conway 定律）；元件邊界清楚，團隊才能平行工作而互不干擾 |
| 部署 | 好的架構讓部署**一鍵完成**，不需要大量腳本 |
| 運行 | 架構要讓系統運行所需的資源（吞吐量、延遲）清楚可見，並保留調整的彈性 |
| 維護 | 主要成本在**探索**（找該改哪裡）與**風險**（改了會不會壞別的），好的架構同時降低兩者 |

### 策略與細節

軟體分成兩個要素：**策略**（業務規則，是價值所在）與**細節**（讓人、其他系統與策略溝通的機制，如 I/O、資料庫、Web、框架）。**好架構讓策略成為核心，細節則是可以延後決定或替換的外掛。**

書中的例子：FitNesse 一開始就**延後**選擇資料庫，用檔案先寫，直到後來發現根本不需要資料庫。這種延後決策讓團隊能在更有資訊時再選擇。

### 獨立性與解耦

好的架構要讓以下各面向彼此獨立：

- **使用案例**（use case）：不同使用案例可以獨立變更。
- **運行**、**開發**、**部署**。

**水平分層**（UI、應用規則、業務規則、資料庫）加上**垂直切分使用案例**，兩個方向都解耦。

解耦的**模式**有三種，各有不同成本：

| 模式 | 說明 |
| --- | --- |
| 原始碼層級 | 同一個可執行檔，只用語言的存取控制隔離 |
| 部署層級 | 不同的 jar／DLL，可獨立部署 |
| 服務層級 | 元件之間透過網路呼叫通訊 |

要選哪種不必一開始決定，可以先在原始碼層級保持良好分離，之後需要時再往下一種移動。

**真重複 vs 假重複。** 兩段程式碼長得一樣，但**因不同理由演進**，就是**偶然的重複**（假重複），不該急著合併；兩處必須同步修改才是**真重複**。

## 邊界

### 邊界是一條線

**邊界**把重要的軟體元素與不重要的分開：業務規則在一邊，GUI、資料庫等細節在另一邊。**依賴箭頭永遠由細節指向業務規則**，所以細節像是「外掛」：資料庫、UI 都可以被抽換，業務規則完全不知道。

比喻：**外掛架構**——像編輯器載入外掛，核心完全不依賴外掛；IDE 外掛的變更不影響編輯器本身。

**邊界的剖析**（邊界可以長什麼樣）：

| 形式 | 說明 |
| --- | --- |
| 單體 | 同一個可執行檔，邊界是原始碼層級的介面與函式呼叫，成本最低 |
| 可部署元件 | jar／DLL，同一行程內 |
| 執行緒 | 邊界仍在同一個行程，但有並行問題 |
| 本地行程 | 同一台機器的不同行程，用 socket 或 IPC |
| 服務 | 透過網路通訊，延遲最高 |

大多數系統混合使用，**越靠近核心的邊界越便宜，越外圍的越昂貴**。

### 策略與層級

**層級（level）= 與輸入輸出的距離**。離 I/O 越遠，層級越高。原則是：**原始碼依賴應該指向高層級策略，而不是反過來**；資料流可以是雙向的，但依賴方向由 DIP 決定。

### 業務規則

| 概念 | 說明 |
| --- | --- |
| **實體**（Entity） | 封裝**關鍵業務規則**，與具體應用無關，是最通用、最不易變的規則，可以被多個應用重用 |
| **使用案例**（Use Case） | 封裝**應用特有**的業務規則，說明輸入、輸出與步驟；控制實體如何互動，**不關心資料如何呈現或儲存** |
| 請求與回應模型 | 使用案例輸入輸出用的**簡單資料結構**，不依賴實體或資料庫列 |

### 尖叫的架構

看一個專案的頂層目錄結構，應該能一眼看出它是什麼系統（例如「醫療記錄」、「訂單」），而不是「這是 Spring／Rails 專案」。**架構要「尖叫」使用案例，而不是框架**。框架只是工具，不是系統的主題；好的架構讓你不需要框架、資料庫、Web 就能測試使用案例。

## 整潔的架構

### 同心圓與依賴規則

整潔架構整合了 Hexagonal、DCI、BCE、Onion 等架構的共同想法，畫成同心圓，由內而外：

```text
最外層  Frameworks & Drivers   Web、DB、UI、設備、外部框架
          │ 原始碼依賴往內
          ▼
        Interface Adapters     Controller、Presenter、Gateway
          │
          ▼
        Use Cases              應用特有業務規則
          │
          ▼
最內層  Entities               關鍵業務規則

依賴規則：原始碼依賴只能由外往內，內層不能知道外層的任何東西
```

| 層 | 內容 | 變動頻率 |
| --- | --- | --- |
| Entities | 企業關鍵業務規則 | 最低 |
| Use Cases | 應用特有規則，協調實體 | 低 |
| Interface Adapters | 在內層格式與外層格式之間轉換（MVC、Presenter、Gateway） | 中 |
| Frameworks & Drivers | 資料庫、Web 框架、UI | 最高 |

### 跨越邊界

控制流需要由外層走到內層、再回到外層（例如：Controller → Use Case → Presenter）。為了讓**原始碼依賴仍由外往內**，在使用案例層定義介面：

```text
Controller ──呼叫──► «interface» InputBoundary ◄──實作── UseCaseInteractor
UseCaseInteractor ──呼叫──► «interface» OutputBoundary ◄──實作── Presenter
```

這是 DIP 的實際應用：使用案例擁有介面，外層去實作。

**跨越邊界的資料**要是**簡單的資料結構**（DTO、參數、`Map` 等），不要直接傳遞實體或資料庫列，否則內層就會依賴外層的格式。

### Humble Object（謙卑物件）

把行為分成**難測試**的部分（與框架、UI、資料庫緊密相關）與**容易測試**的部分，難測試的做到「謙卑」到幾乎沒有邏輯。

| 位置 | 做法 |
| --- | --- |
| **Presenter 與 View** | View 是謙卑物件，只負責把 Presenter 準備好的資料顯示出來；格式化日期、貨幣、按鈕狀態等邏輯放在可測試的 Presenter |
| 資料庫閘道 | 使用案例層定義 Gateway 介面；資料存取層實作它。ORM 是資料庫邊界上的謙卑物件 |
| 服務監聽器 | 只負責接收並轉換資料，邏輯在內層 |

### 部分邊界

完整的邊界（介面 + 輸入輸出模型 + 實作分開）成本很高。如果還不確定是否需要，可以做**部分邊界**：

| 方式 | 說明 |
| --- | --- |
| **略過最後一步** | 把兩邊的元件都做好，但仍在**同一個元件**中，不實際切開成獨立部署的元件；日後需要再切 |
| **單向邊界** | 只做 Strategy 模式：一邊定義介面，另一邊實作，不做對稱的反向介面；缺點是日後依賴可能偷偷反向 |
| **Facade** | 只有一個 Facade 類別當入口，其他類別仍能被直接引用；最簡單，但容易被繞過 |

這是**在現在的成本與未來的彈性之間的取捨**，需要根據風險判斷，不是照單全收。

### 層與邊界

書中用文字冒險遊戲「Hunt the Wumpus」說明：UI、遊戲規則、語言（英語／西班牙語）、資料持久化等都可能是不同的邊界。架構師要**預測**哪些邊界值得現在就做完整，哪些可以先做部分，並隨系統演進**持續評估**。

### Main 元件

`Main` 是系統中**最髒的元件**，也是最低階的策略：它負責**建立所有工廠、策略、全域設施**，把依賴注入進去，然後把控制權交給高階策略。Main 是整個系統的**外掛**，可以有多個 Main（開發、測試、正式環境）。書中提到：可以用 Spring 把依賴注入到 Main，但業務物件本身不該知道 Spring 的存在（不要把 `@Autowired` 之類的註解散在業務規則裡）。補充：在 Spring 專案中，`@Configuration` 這類組裝依賴的程式碼，概念上就落在這個位置。

### 服務：偉大與微小

**服務架構本身不等於好架構**。服務只是邊界的一種形式，只是跨網路。書中指出兩個常見的錯覺：

| 錯覺 | 事實 |
| --- | --- |
| **解耦錯覺** | 服務在網路層分開，不代表在資料、行為上解耦；共用資料表或資料格式時，仍然強耦合 |
| **獨立開發與部署錯覺** | 跨服務的功能變更仍需要協調多個團隊與服務 |

**Kitty 問題**：假設計程車派遣服務現在要新增「送貓」功能，需要改動的是**所有服務**——派遣、價格、訂單……因為功能是橫切多個服務的。要靠**物件導向的元件原則**（用 SRP、OCP、DIP 組織服務內部）才能讓各服務對這類橫切變更保持開放，而不是只靠服務切割。

**以元件為基礎的服務**：服務內部也要有整潔的架構；每個服務可以是一個遵守依賴規則的**元件**，各自用介面與其他服務溝通。

### 測試邊界

測試是**最外層的元件**，依賴系統但不被依賴。測試與系統耦合過緊會造成**脆弱的測試**：一個很小的 GUI 變更讓大量測試失敗，導致開發者不敢改系統。

- 設計的第一原則：**不要依賴易變的東西**。GUI 易變，透過 GUI 的測試就脆弱。
- 做法：建立專門的**測試 API**，讓測試可以繞過 GUI、安全機制、資料庫，強制系統進入特定狀態。它是使用案例與介面轉接器的**超集合**。
- **結構耦合**是最強也最隱蔽的耦合：每個類別一個對應的測試類別、每個方法一個測試方法。重構任何類別都會讓大量測試中斷。測試 API 把測試與應用的結構解耦，讓兩者**獨立演進**：測試越來越具體，產品程式越來越通用。
- 測試 API 具有超能力，若部署在正式環境會有安全風險，應放在**獨立的元件**中。

### 整潔的嵌入式架構

書中引用 Kent Beck 的名言：「先讓它運作，再讓它正確，再讓它快。」嵌入式開發常卡在**目標硬體瓶頸**（只有硬體做出來才能測試）。解法是用**層**把軟體與韌體、硬體分開，加上**硬體抽象層（HAL）**、**處理器抽象層**、**作業系統抽象層**，並避免滿地的條件編譯（`#ifdef`）。這樣大部分程式碼可以在開發主機上測試。

## 細節

細節是「輸入輸出」、「儲存」、「呈現」的機制，不是策略的一部分。三件事被書歸為**細節**：

| 章節 | 觀點 |
| --- | --- |
| **資料庫是細節**（第 30 章） | 資料**模型**（關聯式、表、列）對架構重要，但**資料庫技術**本身是儲存機制。資料庫存在是因為磁碟旋轉慢；若記憶體足夠便宜，資料可能直接放 RAM，用一般資料結構。業務規則不該知道資料如何儲存 |
| **Web 是細節**（第 31 章） | Web 是 I/O 設備，是一種傳遞機制。GUI 與業務規則應該分開。架構擺盪：從瘦客戶端到胖客戶端又回來，一直在變，所以不要讓業務規則依賴它 |
| **框架是細節**（第 32 章） | 與框架的關係是**不對稱的婚姻**：你對框架做出全部承諾，框架對你什麼都不承諾。框架作者的目標與你的不同；框架可能越來越大、升級強迫你改動。**不要與框架結婚**——把框架保持在外層，不讓業務規則繼承框架的類別或散布框架的註解；依賴注入框架（如 Spring）應限制在 Main 附近 |

## 案例與組織程式碼

### 案例研究：影片販售

書中以一個影片販售網站為例：先找出**角色**（觀眾、購買者、管理者、作者）與**使用案例**，再依 SRP 為每個角色群組切出使用案例，最後處理元件與依賴方向。目的是示範：從使用案例出發，而不是從資料庫表、框架出發。

### 遺漏的章節：四種組織程式碼的方式

第 34 章（Simon Brown 所寫）比較：

| 方式 | 說明 | 問題 |
| --- | --- | --- |
| **依層打包** | `web`、`service`、`data` 各一個套件 | 新功能要在每層都改；容易跳過層（寬鬆的分層，如 Controller 直接用 Repository） |
| **依功能打包** | 每個功能（訂單、客戶）一個套件，包含所有層 | 功能清晰，但層次不明顯 |
| **連接埠與轉接器** | 內部是業務邏輯，外部是各種轉接器（Web、DB） | 需要更多嚴格紀律與抽象 |
| **依元件打包** | 把與一個粗粒度元件相關的業務邏輯與資料存取**打包在一起**，外部只能經由元件的**公開介面**使用，內部實作隱藏 | 混合方式，目標是封裝 |

書中強調**實作細節是魔鬼**：光有好的設計，若所有類別都標記為 `public`，其他人仍會繞過架構；要靠**編譯器強制**（存取修飾詞、獨立的原始碼樹、獨立的編譯單元）來實現。組織（結構）與封裝（隱藏）是兩件不同的事，兩者都要做。

## 速查：整潔架構的重點

| 概念 | 一句話 |
