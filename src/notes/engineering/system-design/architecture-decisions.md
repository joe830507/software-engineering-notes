# 架構決策、溝通與自測

> 對應《軟體架構原理》Part III：技巧與軟技能（第 19–24 章）。前面談的是「選什麼」，這一頁談**怎麼記錄決策、評估風險、畫圖溝通、帶團隊**，最後提供橫跨三本書的面試自測。

## 架構決策

### 常見的反模式

書中指出架構師做決策時三個常見的反模式，**依序出現**：克服第一個之後會遇到第二個，再克服才會遇到第三個。

| 反模式 | 說明 | 解法 |
| --- | --- | --- |
| **掩蓋資產（Covering Your Assets）** | 因為怕做錯，逃避或拖延決策 | ① 等到**最後不得不做決策的時刻**：資訊已足夠，又不會久到拖累團隊或掉入分析癱瘓；② 與**開發團隊合作**，確認決策能如預期實現，必要時快速調整（例如書中的複製快取案例：團隊發現某些服務記憶體不夠，架構因此調整） |
| **土撥鼠日（Groundhog Day）** | 大家不清楚**為什麼**這樣決定，同樣的問題被反覆討論 | 提供**技術與商業**兩方面的理由。商業理由是檢驗決策的試金石：若無法帶來商業價值，或許就不是好決策。最常見的四種：**費用、上市時間、使用者滿意度、策略定位**；還要看利益相關方真正在乎的是什麼 |
| **電子郵件驅動架構** | 決策被遺失、遺忘或沒有傳達給該知道的人，導致無法實現 | ① 不要把決策放在信件**內文**，而是放在**單一記錄系統**（wiki 頁面或文件），信中只寫決策性質並附連結；② 只通知**在乎**這個決策的人（句型像「我做了一個會直接影響你與某服務之間通訊的重要決定」） |

### 在架構上至關重要

書中界定「架構決策」是影響下列任一項的決策：

- **結構**：例如選擇微服務。
- **非功能性特性**：例如影響效能與擴展。
- **依賴性**：元件之間如何耦合。
- **介面**：服務如何被存取。
- **建構技術**：框架、函式庫、平台、工具。

### 架構決策紀錄（ADR）

ADR 是**一頁的短文件**，記錄單一決策。書中的基本結構：

| 段落 | 內容 |
| --- | --- |
| **標題** | 循序編號 + 簡短描述，例如「ADR 42：在訂購與付款服務間使用非同步傳訊」 |
| **狀態** | **提議**（等待核准，尚未實作）、**接受**（已核准，可以實作）、**取代**（已被另一個 ADR 取代，並互相標註）。需要意見時可以標為**RFC**並設定截止日期 |
| **背景** | 這個決策面對的**力量**：需求、限制、選項 |
| **決策** | 選了什麼，**以及為什麼**；用「我們將……」的主動語氣，比「應該」更清楚 |
| **後果** | 決策的影響，包含**取捨分析**——被拒絕的方案、犧牲了什麼 |
| **治理**（書中強烈建議加入） | 如何驗證決策被遵守，包含適應度函數 |
| **註解**（書中強烈建議加入） | 作者、核准日期、修改紀錄等中繼資料 |

要點：

- **取代關係**要互相連結：ADR 42 被 ADR 68 取代（例如從非同步傳訊改成 REST），這個歷史軌跡能避免有人再次提出已被否決的方案。
- **儲存位置**：與原始碼放在 Git 有版本與追蹤；但多數情況建議放 **wiki**（有目錄結構，方便非開發人員閱讀，也能放更多背景資訊）。結構可依範圍分：企業 ADR、應用程式 ADR、整合 ADR。
- **ADR 當作文件**：決策、理由、後果都有了，比單靠架構圖更能說明「為什麼」。
- **ADR 當作標準**：標準常因為沒人知道為什麼而被忽略；把標準寫成 ADR，附上背景與後果，會更容易被接受與遵循。

## 架構風險分析

### 風險矩陣

用兩個維度判斷風險：**影響**與**發生可能性**，各分低（1）、中（2）、高（3），**相乘**得到客觀分數：

| 分數 | 等級 |
| --- | --- |
| 1–2 | **低**風險 |
| 3–4 | **中**風險 |
| 6–9 | **高**風險 |

使用技巧：**先考慮影響，再考慮可能性**。例子：中心化資料庫若當掉，影響可能是「高」；但因為資料庫是叢集組態且有備援，發生可能性是「低」，交叉後整體風險為 3（中）。

### 風險評估

把各個**架構特性**（可用性、可擴展性、資料完整性、效能等）乘上各個**架構區域**（服務、資料庫、介面等）的風險分數，就得到一張**風險評估**表，可以用累積分數看出整體上哪個特性或哪個區域風險最高；也可以過濾，只展示高風險區，用在向主管簡報。評估要**定期重做**，因為風險隨時間變化。

### 風險激盪

**風險激盪（risk storming）**是多位架構師與技術領導**共同**判斷架構風險的活動，分兩部分：

| 階段 | 說明 |
| --- | --- |
| 個人（確認風險） | 每位參與者**各自**用風險矩陣，在架構圖上標出風險區域，**不互相討論**，避免互相影響。書中的做法是準備綠、黃、紅三色小便利貼，寫上風險分數貼在圖上 |
| 共同（共識與減緩） | 大家一起對風險區域達成共識，找出降低風險的方案，也可能因此修改設計 |

常見的風險維度包括：**可擴展性、效能、可用性、資料損失、單點故障、安全性**。

## 圖解與簡報

### 圖解標準

| 標準 | 說明 |
| --- | --- |
| **UML** | 統一了 1980 年代三種物件導向建模哲學；但在要求使用它的組織以外影響有限。類別圖與循序圖仍被用來溝通，其餘大多已少用 |
| **C4** | Simon Brown 提出，彌補 UML 的不足。四個層次：**Context**（系統背景，使用者與外部依賴）、**Container**（實體／邏輯部署邊界與容器）、**Component**（元件）、**Code**（類別圖，仍用 UML） |
| **ArchiMate** | 開放的企業架構建模語言（Open Group 標準），目標是「越小越好」，描述業務領域內及跨領域的架構 |

書中說：若公司想在畫圖技巧上標準化，C4 是不錯的選擇，但沒有標準能表達架構師可能用到的**每種**設計（尤其是微服務這類分散式系統）。

### 好的圖要有

| 要素 | 建議 |
| --- | --- |
| **標題** | 圖上所有元素都有標題，或確定是聽眾熟知的 |
| **線條** | 夠粗才看得清；箭頭表示資料流向要一致。常見慣例：**實線表同步，虛線表非同步** |
| **形狀** | 軟體圖沒有普遍標準形狀，可以建立自己的一組，並用**模板**維持一致 |
| **標籤** | 每個元素都要標註，不依賴聽眾猜測 |
| **顏色** | 不要只用顏色傳遞資訊，因為可能被黑白列印或有人色盲 |
| **圖例** | 若形狀或顏色有特殊意義，要附圖例 |

### 簡報

書中區分**資訊簡報（infodeck）**與**簡報（presentation）**：infodeck 是**被閱讀**的投影片（內容完整、可以獨立讀懂），presentation 是**被講述**的投影片（簡潔、搭配講者）。**投影片只佔故事的一半**，另一半是講者怎麼說。

## 團隊與軟技能

### 團隊界限

架構師為團隊設定**界限**：太緊讓開發人員沒有空間，太鬆又缺乏引導。書中以三種人格型態比喻：

| 型態 | 界限 | 結果 |
| --- | --- | --- |
| **控制狂**架構師 | 太緊 | 開發人員被限制、不滿 |
| **空談**架構師 | 太鬆 | 缺乏引導，團隊自行決策，造成混亂 |
| **有效**架構師 | 依情境調整 | 看團隊熟練度、專案複雜度、時程；對新手更緊，對資深者更鬆 |

### 團隊警告信號

書中用三個現象判斷團隊大小是否合適：

| 信號 | 說明 |
| --- | --- |
| 流程損失 | 團隊越大，協調成本越高，產能沒有成比例成長 |
| **多數無知** | 大家表面上都同意，但其實各自私下不同意，卻沒人說出來（書中用「國王的新衣」比喻）；架構師要扮演推動者，讓人敢說話 |
| **責任分散** | 團隊越大，個人越覺得「應該有別人負責」 |

### 檢查清單

架構師可以用**檢查清單**提高團隊品質，書中舉三種：**開發人員的程式碼完成度**、**單元與功能測試**、**軟體發行**。

常見問題是開發人員為了趕時間，只是把項目全部打勾。書中的對策：向團隊說明清單的重要性與理由（可推薦《清單革命》）、讓成員一起決定清單上有哪些項目；若仍不行，可利用**霍桑效應**——讓大家知道清單會被**抽查**，被觀察時人們通常會做對的事。

### 交涉與領導

| 情境 | 技巧 |
| --- | --- |
| 與業務利益相關方 | 把決策與**業務價值**連結，用他們的語言說，而不是技術術語 |
| 與其他架構師 | 避免爭論與個人情緒，用取捨與證據討論 |
| 與開發人員 | 說明**為什麼**，而不是命令；請求幫忙時使用名字與具體說明，不要用要求的口吻 |

書中提出的**架構的 4 個 C**：**溝通、協作、清晰、簡明**，用來避免因過度複雜而產生的偶然複雜度。

架構師也應是**務實但有遠見**的領導者：用策略思考規劃未來，但解決方案要切實可行，不能太理論化。

### 發展職涯

**20 分鐘法則**：每天至少花 20 分鐘學習（技術雷達、文章、論文），維持**技術廣度**；用 ADR 與簡報練習溝通；保持動手，並在實務中練習取捨判斷。

## 面試自測

### 20 題口頭自測

先遮住答案，每題用 30–60 秒回答。

| 題目 | 答案關鍵 |
| --- | --- |
| 1. 系統設計面試的四步驟與時間分配？ | 了解問題 3–10、高階設計 10–15、深入 10–25、總結 3–5 分鐘 |
| 2. 為什麼 Web 層要無狀態？ | session 移到共用儲存，才能自動加減伺服器、容易故障轉移 |
| 3. 快取要注意哪些事？ | 何時用、過期、一致性、單點故障、逐出策略 |
| 4. 推 vs 拉扇出怎麼選？ | 一般使用者用推，名人用拉，降低大量寫入扇出的壓力；熱門讀取仍需快取或副本 |
| 5. Token 桶與固定視窗計數器各有什麼問題？ | Token 桶：參數難調；固定視窗：邊界突發超限 |
| 6. 為什麼取餘數的分片擴容很糟？ | N 改變後幾乎所有 key 重新映射，快取大量失效 |
| 7. 一致性雜湊為什麼需要虛擬節點？ | 解決分區大小與 key 分佈不均 |
| 8. `W + R > N` 代表什麼？ | 同一固定副本集合內，讀寫 quorum 必有交集；仍需處理版本、並行與失敗操作，不能單靠此式保證強一致 |
| 9. CAP 中為什麼實務上沒有 CA？ | 網路分區無法避免，分散式系統必須有 P |
| 10. 短網址為何用 Base 62 轉換？7 碼夠嗎？ | 唯一 ID 完整轉換後不碰撞；7 碼容量足夠，但 ID 必須小於 62^7，Snowflake 不保證符合 |
| 11. Snowflake 的 64 位元怎麼分？ | 1 + 41 時間戳 + 5 資料中心 + 5 機器 + 12 序列 |
| 12. 聊天系統為什麼用 WebSocket？ | 雙向持久連線，輪詢浪費、長輪詢仍有缺點 |
| 13. 通知系統怎麼避免重複？ | 無法 exactly-once，用事件 ID 去重並搭配重試 |
| 14. 自動補全如何達到 O(1) 查詢？ | 限制前綴長度 + 每個 trie 節點快取 top-k |
| 15. 為什麼 SRP 說「對一個角色負責」？ | 不同角色因不同理由要求變更，混在一起會互相影響 |
| 16. 什麼是依賴反向？ | 讓原始碼依賴指向抽象／高階策略，細節實作它，控制流與依賴方向可相反 |
| 17. 穩定依賴與穩定抽象原則的指標？ | I = Fan-out/(Fan-in+Fan-out)；A = 抽象類別/類別總數；D = \|A+I−1\| |
| 18. 架構第一法則是什麼？ | 一切皆是取捨；為什麼比如何更重要 |
| 19. 架構量子是什麼？為什麼重要？ | 可獨立部署、高功能性內聚、同步共生性；整體特性受最弱量子限制 |
| 20. ADR 有哪些段落？ | 標題、狀態、背景、決策、後果，加治理與註解 |

### 整合題：設計「短網址服務」並討論內部結構

這題可以把三本書接起來回答：

1. **規模與估算**（面試指南）：每天 1 億寫入 → 1,160 QPS 寫、11,600 QPS 讀、10 年 3,650 億筆。
2. **高階設計**（面試指南，加上 ID 範圍補充）：無狀態 Web 層 + 快取 + 關聯式資料庫 + 唯一 ID + Base 62 轉換。固定 7 碼採受控範圍的序號／號段；若選 Snowflake，須接受較長短碼。
3. **特性取捨**（軟體架構原理）：可用性與可擴展性是主要特性，重定向以讀取為主；301 對 302 就是特性取捨（負載 vs 可分析）。
4. **選架構風格**（軟體架構原理）：規模不大時，**模組化單體**加獨立的資料存取就夠；讀寫比例極不對稱時，才考慮拆出讀取服務。
5. **內部結構**（Clean Architecture）：使用案例（縮短、重定向）在核心，儲存與 ID 生成透過介面（Gateway）注入，換掉資料庫不會影響使用案例；框架保持在外層，由 Main 組裝。
6. **記錄決策**（軟體架構原理）：用 ADR 記錄「為什麼選 302 而不是 301」「短碼長度限制與 ID 生成策略如何取捨」，並用適應度函數驗證延遲目標。

### 常見追問

| 追問 | 方向 |
| --- | --- |
| 資料量再成長 10 倍怎麼辦？ | 分片（一致性雜湊）、讀寫分離、快取、CDN |
| 資料中心掛了？ | 多資料中心、跨區複寫、故障轉移 |
| 如何證明設計符合目標？ | 估算 + 負載測試 + 適應度函數 |
| 為什麼不直接上微服務？ | 微服務的成本與複雜度；先用模組化單體，有真實需求再拆 |
| 要怎麼降低維護成本？ | 依賴規則、邊界、ADR、自動化治理 |
