# 軟體架構基礎：思維、模組化與架構特性

> 對應《軟體架構原理：工程方法》（Mark Richards、Neal Ford）Part I：基礎（第 1–9 章）。前面兩本書談的是「怎麼畫圖」與「程式碼怎麼放」，這一頁談**架構師怎麼思考、怎麼測量、怎麼決定**。

## 定義與架構師的角色

### 軟體架構的四個面向

書中定義軟體架構由四部分組成：

| 面向 | 說明 |
| --- | --- |
| **結構** | 系統採用的架構風格（微服務、分層、微核心……） |
| **架構特性** | 系統成功所需的「-ilities」（可擴展性、可用度……） |
| **架構決策** | 系統怎麼做的規則（例如「只有業務層與服務層可存取資料庫」） |
| **設計原則** | 做決策時的**指引**（例如「服務間通訊盡量非同步」） |

### 兩條法則

| 法則 | 意思 |
| --- | --- |
| **第一法則：軟體架構的一切皆是取捨** | 沒有最佳解，只有針對某個脈絡下較好的解。若你以為找到了不是取捨的東西，更可能是還沒找到取捨在哪 |
| **第二法則：為什麼，比如何更重要** | 看架構圖能知道**如何**，但不知道**為什麼**這樣選，因此決策要被記錄（見「架構決策」頁的 ADR） |

### 對架構師的期望

| 期望 | 說明 |
| --- | --- |
| 做架構決策 | 提供**引導**，而不是替開發人員指定每一種技術選擇 |
| 持續分析架構 | 架構會隨時間腐化，要持續檢查「結構衰退」 |
| 跟上最新趨勢 | 架構決策長期持續，要了解新技術與範式 |
| 確保決策的符合度 | 確認開發團隊真的遵循決策與設計原則 |
| 廣泛的暴露與經驗 | 技術**廣度**比深度重要 |
| 業務領域知識 | 能用利益相關方聽得懂的方式溝通 |
| 人際關係技巧 | 團隊合作、領導、交涉 |
| 了解並駕馭辦公室政治 | 幾乎所有決策都會被挑戰，需要交涉技巧 |

書中引用 Gerald Weinberg：「不管問題看起來是什麼，總是跟人有關的問題。」

### 架構與工程實務、運維、程序

| 交集 | 說明 |
| --- | --- |
| **工程實務** | 從極限程式設計（XP）、持續整合與交付，到 DevOps，工程實務的進步讓架構有更多可能（如自動化部署之於微服務） |
| **運維／DevOps** | 微服務這類架構把運維考量交給運維團隊與自動化機制處理，簡化架構本身；Pets.com 的例子說明：沒有規模彈性，訂單一湧入就失敗 |
| **開發程序** | 現代架構假設以**敏捷**迭代為基準；因為有「未知的未知」，所有架構都會變成迭代式 |
| **資料** | 程式與資料是共生的，架構要考慮資料儲存 |

### 演進式架構與適應度函數

書中提出：**適應度函數（fitness function）**是對某個架構特性做**客觀評估**的機制，可以是指標、單元測試、監控等，用來**持續驗證**架構是否仍符合重要特性。例如把「頁面載入時間」定為重要特性，就用自動化測試在 CI 中測量。這個概念借自演進式計算，讓架構特性可以**自動化治理**。

## 架構思維

### 架構與設計的差別

傳統觀點：架構師決定架構特性、架構風格、元件；開發人員負責每個元件的類別圖與 UI。書中認為這條線其實是**模糊**的，兩者緊密整合，需要雙方協作，不能「丟過牆」。

### 技術廣度

書中把知識分成三類：

| 類型 | 說明 |
| --- | --- |
| 你知道你知道的 | 你的專長（技術深度） |
| 你知道你不知道的 | 聽過但不熟的技術 |
| 你不知道你不知道的 | 完全沒聽過的 |

開發人員的價值通常在**深度**；架構師的價值則在**廣度**——知道更多選項與取捨，而不是在單一技術上知道最多。因為廣度有保質期，書中建議每天花至少 **20 分鐘**學習（讀技術雷達、論文、部落格）來維持。

### 分析取捨

選擇「事件主題（topic）」還是「佇列（queue）」就是典型取捨：主題可以讓之後的消費者隨時加入而不需修改發送方，擴充性好，但沒有訂閱者資訊，安全性與合約管理較差；佇列則相反。不要問「哪個好」，要問「在這個脈絡下，什麼比較重要」。

### 了解業務驅動因素

把業務目標（上市時間、成本、規模、合規）**轉成**架構特性，這是架構師的核心工作之一。

### 平衡架構與程式編寫

架構師需要保持動手能力，但要避開**瓶頸陷阱**：架構師負責的程式碼若在專案**關鍵路徑**上，會因為要處理會議、決策、其他事務而拖慢團隊。書中的對策：

- 把關鍵路徑與框架程式碼**交給開發團隊**，架構師改做商業邏輯相關的程式碼（例如某個非關鍵的服務或畫面）。
- 常做**概念驗證（POC）**，而且盡量寫出**產品等級**的程式碼：一次性的 POC 程式碼常被放進程式庫、被當成參考；寫成產品等級也能真正檢驗設計是否可行。
- 常進行**程式碼審查**：架構師即使沒在寫程式，也能保持與原始碼的聯繫，並確認團隊遵循架構。

## 模組化

### 模組、元件與內聚

書中用**模組**指「一群相關程式碼的通用名稱」，**元件**則是邏輯或實體的分組。

**內聚（cohesion）** 指模組內各部件彼此相關的程度。從最好到最差：

| 類型 | 說明 |
| --- | --- |
| 功能內聚 | 模組每個部件都與其他部分相關，擁有完整功能 |
| 順序內聚 | 一個模組的輸出是另一個的輸入 |
| 通信內聚 | 模組形成通信鏈，操作同一份資料 |
| 程序內聚 | 必須以特定順序執行 |
| 時間內聚 | 時間上相依（例如啟動時初始化的一串任務） |
| 邏輯內聚 | 資料邏輯上相關，功能上卻無關（如一堆 `String` 靜態工具方法） |
| 偶然內聚 | 只是剛好在同一個檔案 |

書中承認內聚指標比耦合不精確，**有主觀性**，常需架構師判斷。可量化的指標有 **LCOM**（類別方法缺乏內聚程度）：沒有共享欄位的方法越多，分數越高，表示內聚越差。

### 耦合與可量化指標

| 指標 | 說明 |
| --- | --- |
| 傳入耦合（Ca） | 有多少外部元件依賴它 |
| 傳出耦合（Ce） | 它依賴多少外部元件 |
| **抽象性** | 抽象工件（介面、抽象類別）占全部工件的比例 |
| **不穩定性** | `I = Ce / (Ce + Ca)`；越高越易變，因為依賴的東西變時它就可能壞 |
| **主序列距離** | `D = \|A + I − 1\|`，越接近 0 越理想（與 Clean Architecture 的主序列相同概念） |

### 共生性（connascence）

**定義：** 兩個元件共生，如果其中一個改變，另一個也必須改變以維持整體正確。書中以此取代傳統的「耦合」來描述更細緻的依賴。分為**靜態**（程式碼可靜態分析）與**動態**（執行時行為）。

| 靜態共生性 | 說明 |
| --- | --- |
| 名稱（CoN） | 多個實體要使用相同名稱，如方法名稱 |
| 型別（CoT） | 多個實體要使用相同型別 |
| 含義／慣例（CoM／CoC） | 多個實體必須對值的含義有共識，如 `1` 代表啟用、`-1` 代表 null |
| 位置（CoP） | 參數順序必須一致 |
| 演算法（CoA） | 多個實體必須用相同的演算法，如雜湊與驗證 |

| 動態共生性 | 說明 |
| --- | --- |
| 執行（CoE） | 執行順序有關 |
| 時序（CoT） | 執行的時序有關 |
| 值（CoV） | 多個值同時變動 |
| 識別（CoI） | 多個實體必須引用同一物件 |

共生性的特性：**強度**（越容易重構越弱，名稱最弱）、**局部性**（越接近越好，同一個模組內的強耦合比跨模組好）、**程度**（影響多少個實體）。兩個建議：**降低**跨邊界的共生性強度，**提高**同邊界內的共生性。

## 架構特性

### 什麼是架構特性

架構特性是系統**成功所需**、**與業務領域無關**的設計考量。書中的三個準則（要同時滿足）：

1. 指定與領域無關的設計考量。
2. 影響設計的某些**結構**面向。
3. 對應用程式的成功至為關鍵或重要。

不用「非功能性需求」，因為有貶低意味；不用「品質屬性」，因為偏向設計後的評估；選用「架構特性」，強調它們塑造架構。

**隱含與顯性**：顯性特性出現在需求文件；隱含特性（如可用性、可靠度、安全性）很少被提及，但專案成功需要，架構師要用領域知識找出來（例如高頻交易公司的低延遲）。

### 分類

| 類別 | 例子 |
| --- | --- |
| **運維** | 可用性、持續性、效能、可恢復性、可靠性／安全性、強健性、可擴展性、**彈性**（應付突發量） |
| **結構** | 可配置性、可擴展性（擴充）、可安裝性、可重用性、本地化、可維護性、可移植性、可支援性、可升級性 |
| **跨領域** | 無障礙、可歸檔、認證、授權、合法性、隱私、安全性、可支援性、可用性／可行性 |

書中提醒：**清單永遠不完整**，也沒有標準清單（ISO 有一份可參考）。還舉了「可義大利性」的例子：一家公司因為與義大利分部通訊中斷造成傷害，團隊就把「失聯也要能運作」的需求叫做「可義大利性」，是可用度、可靠度、可恢復性、彈性的獨特組合。

### 挑選要少

**不要追求所有特性。** 每一項特性都會增加設計複雜度，且多數特性彼此拉扯（例如安全性與效能）。書中建議：從**領域考量**、**需求**、**隱含領域知識**取出特性，再跟利益相關人**排出優先順序**，只挑少數真正重要的（書中的案例是列出前三名）。

### 測量與治理

| 類型 | 說明 |
| --- | --- |
| 運維測量 | 效能（回應時間、百分位）、可擴展性、彈性，可由負載測試取得 |
| 程序測量 | 可測試性（程式碼覆蓋率）、可部署性（部署成功率與時間） |
| 結構測量 | 圈複雜度、元件耦合、循環依賴 |
| **治理** | 用**適應度函數**自動檢查，例如架構測試工具驗證層次規則，或在 CI 加入複雜度門檻 |

## 範圍：架構量子與顆粒度

### 架構量子

> **架構量子**：具備高功能性內聚與同步共生性、可被獨立部署的工件。

| 部分 | 說明 |
| --- | --- |
| 可獨立部署 | 包含獨立運作所需的**所有**元件，包括資料庫；共用資料庫的多個服務屬於同一個量子 |
| 高功能性內聚 | 為了單一目的，微服務下通常對應一個工作流程（限界上下文） |
| **同步共生性** | 同步呼叫會讓兩端的運維特性必須接近，所以同步呼叫的服務屬於同一個量子；**非同步通訊**才能讓兩邊的特性不同 |

為什麼重要：整個系統的運維特性（如可擴展性）受**最弱量子**限制。單體分層架構通常只有**一個**量子；微服務架構每個服務各有自己的資料庫，所以有**多個**量子；事件驅動架構的量子數可以是一到多個，取決於資料庫與同步共生性。

### 單體 vs 分散式

| | 單體 | 分散式 |
| --- | --- | --- |
| 部署單位 | 一個 | 多個，透過網路通訊 |
| 優點 | 簡單、便宜 | 可獨立擴展、部署、容錯 |
| 缺點 | 規模上限、變更風險 | 要處理網路 |

**分散式運算的八個謬誤**（書中全列）：

1. 網路是可靠的。
2. 延遲為零。
3. 頻寬是無限的。
4. 網路是安全的。
5. 網路拓撲不會改變。
6. 只有一位管理員。
7. 傳輸成本為零。
8. 網路是同質的。

分散式還要考慮分散式日誌、分散式交易、版本與合約維護等。

## 元件為基礎的思維

### 元件的範圍

元件是架構的**建構方塊**，是邏輯分組（命名空間、套件）。第一件要決定的事：**最上層怎麼分割**。

| 分割方式 | 說明 |
| --- | --- |
| **技術分割** | 依技術能力分層：展示、業務規則、持久、資料庫（分層架構） |
| **領域分割** | 依領域或工作流程分：客戶、訂單、付款（微服務、模組化單體） |

領域分割容易讓一個領域的變更只影響一處，但需要有人了解領域；技術分割較容易，但領域變更會同時影響多層。取捨取決於團隊結構與變更類型。

### 發現元件的流程

書中的流程是迭代的：**確認初始元件 → 把需求指定給元件 → 分析角色與責任 → 分析架構特性 → 重構元件**。可以用的技巧有：

- **實體陷阱（Entity Trap）**：不要為需求中每個實體都建一個元件（例如拍賣、項目、出價各一個），這只是從框架到資料庫的物件關聯對映，不是架構；沒有工作流程與行為。
- **角色／行動法**：識別系統的角色與他們的行動，再把行動歸到元件。
- **工作流程法**：依工作流程找出元件。

書中用兩個案例貫穿：**Silicon Sandwiches**（單體）與**繼續、繼續、成交**（Going, Going, Gone，分散式拍賣）。

### 還原架構量子：選單體或分散式

決定單體或分散式要看架構特性：

- 單一量子就夠：簡單、成本低的系統。
- 需要不同部分有不同的可擴展性、可用性或彈性（例如拍賣系統的出價與瀏覽要求不同）：考慮多個量子。

## 小結：架構師的檢查清單

| 問題 | 對應概念 |
| --- | --- |
| 這個決策的取捨是什麼？ | 第一法則 |
| 為什麼這樣選？有記錄嗎？ | 第二法則、ADR |
| 業務真正在乎什麼？ | 架構特性（少數） |
| 怎麼證明架構持續符合？ | 適應度函數 |
| 這兩個元件變動時會互相影響嗎？ | 共生性、耦合 |
| 系統需要幾個獨立部署與擴展的單位？ | 架構量子 |
| 最上層怎麼切？ | 技術分割 vs 領域分割、避開實體陷阱 |
