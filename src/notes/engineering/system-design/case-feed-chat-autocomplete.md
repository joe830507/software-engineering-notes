# 案例：動態訊息、聊天系統、搜尋自動補全

> 對應《系統設計面試指南》第 11–13 章。三題分別代表三種典型壓力：**扇出**（一份資料要送給很多人）、**長連線與狀態**（即時雙向通訊）、**低延遲查詢**（100 毫秒內回應）。

## 動態訊息系統

動態訊息（news feed）是首頁中間持續更新的內容列表。Facebook 動態、Instagram feed、Twitter timeline 都是同一類問題。

### 需求

書中假設：行動 App 與 Web 都要；使用者可發佈貼文、可看朋友的動態；**依時間倒序**；包含圖片與影片；每天 1,000 萬 DAU。

### API

| 用途 | 請求 |
| --- | --- |
| 發佈貼文 | `POST /v1/me/feed`，參數 `content`、`auth_token` |
| 取得動態訊息 | `GET /v1/me/feed`，參數 `auth_token` |

### 兩個流程

| 流程 | 說明 |
| --- | --- |
| **發佈貼文**（feed publishing） | 貼文寫入快取與資料庫，並送進朋友的動態訊息 |
| **建構動態訊息**（news feed building） | 依時間倒序匯整朋友的貼文 |

### 發佈貼文的細節

Web 伺服器先做**身份驗證**與**限流**（限制一定時間內的貼文數量，以阻止垃圾訊息），再交給：

| 服務 | 職責 |
| --- | --- |
| 貼文服務 | 把貼文存入資料庫與快取 |
| **扇出服務** | 把新貼文推送給朋友的動態訊息 |
| 通知服務 | 通知朋友有新內容，並發推送 |

### 扇出：推 vs 拉

| | 寫入時扇出（push） | 讀取時扇出（pull） |
| --- | --- | --- |
| 做法 | 發文時就預先算好，立即放進每個朋友的動態快取 | 使用者載入首頁時才即時拉取朋友的最新貼文 |
| 優點 | 讀取很快；動態是即時生成 | 對不活躍使用者不浪費運算；避免發文時對大量追蹤者寫入 |
| 缺點 | 朋友很多時取得朋友清單與建立動態很慢（**熱鍵問題**）；對不活躍使用者浪費運算 | 沒有預先處理，取得動態比較慢 |

書中採用**混合式**：大多數使用者用**推**，因為快速取得動態很重要；擁有大量朋友／追蹤者的名人，改讓追蹤者在讀取時**拉**，降低寫入扇出的壓力。**補充：** 拉取仍可能造成熱門貼文的讀取熱點。一致性雜湊可改善多個 key 的分布，但不能自行拆散單一熱鍵；熱門內容仍需快取、副本等措施。

**扇出服務的流程：**

1. 從**圖資料庫**取得朋友 ID（圖資料庫很適合管理朋友關係與推薦）。
2. 從**使用者快取**取得朋友資訊並過濾，例如被你靜音（mute）的人，或貼文只分享給特定朋友。
3. 把朋友清單與新貼文 ID 送進訊息佇列。
4. 扇出 worker 從佇列取出資料。
5. 把 `<post_id, user_id>` 存入**動態訊息快取**。只存 **ID**，不存完整物件以省記憶體，並設上限（可設定）：使用者很少捲到成千上萬則之外，所以快取未命中率仍然低。

### 取得動態訊息

1. 客戶端送出 `/v1/me/feed`。
2. 負載平衡器轉給 Web 伺服器，再呼叫動態訊息服務。
3. 動態訊息服務從動態快取取得一批貼文 ID。
4. 再從**使用者快取**、**貼文快取**取得完整的使用者與貼文物件，建構完整動態（含使用者名稱、頭像、貼文內容、圖片）。
5. 以 JSON 回傳給客戶端渲染。**媒體檔（圖片、影片）放 CDN。**

### 五層快取

| 層 | 內容 |
| --- | --- |
| 動態訊息 | 動態 ID |
| 內容 | 每則貼文資料；最熱門的放**熱門快取** |
| 社群圖譜 | 使用者關係 |
| 動作 | 是否按讚、回覆等 |
| 計數器 | 讚數、回覆數、追蹤者數、關注數 |

### 可以接著聊

SQL vs NoSQL、主從複寫、無狀態 Web 層、盡量快取、用訊息佇列解耦、監控指標（高峰 QPS、使用者刷新動態的延遲）。

## 聊天系統

書中設計 Facebook Messenger 類型的應用，重點是**低延遲一對一**、**小型群組聊天（最多 100 人）**、**多設備登入**，系統規模為 **5,000 萬 DAU**。

### 客戶端與伺服器的通訊協定

| 協定 | 運作 | 問題 |
| --- | --- | --- |
| HTTP（發送端） | 客戶端發起，keep-alive 維持連線 | 伺服器沒辦法主動送訊息給接收者 |
| **輪詢** | 客戶端定期問「有新訊息嗎？」 | 大多數情況沒答案，**浪費資源** |
| **長輪詢** | 連線保持到有訊息或逾時，收到後立刻再發新請求 | 發送端與接收端可能連到不同伺服器；伺服器難以知道客戶端是否斷線；沒有訊息時仍會定期重連，仍不夠有效率 |
| **WebSocket** | 由客戶端發起，從 HTTP 握手**升級**為雙向持久連線 | 需要有效率的連線管理 |

書中選擇 **WebSocket**，同時用於發送與接收，可簡化設計。但並不是所有功能都要用 WebSocket：登入、註冊、使用者個人檔案等仍用 HTTP 請求／回應。

### 三類服務

| 類別 | 內容 |
| --- | --- |
| **無狀態服務** | 登入、註冊、個人檔案等，由負載平衡器導向；可以是單體也可以是微服務；**服務探索**屬於這類，提供客戶端要連的聊天伺服器清單 |
| **有狀態服務** | 聊天伺服器——客戶端與伺服器維持持久連線，連線不會輕易換伺服器 |
| **第三方整合** | **推送通知**，使用者即使沒開 App 也能收到 |

書中估算：100 萬個同時在線使用者，連線大約只需 10 GB 記憶體（很粗略，與語言有關），理論上單機放得下；但單一伺服器有**單點故障**的風險，所以不能這樣設計。

### 高階元件

聊天伺服器（WebSocket 傳訊）、連線狀態（presence）伺服器、API 伺服器（登入、註冊、改個人檔案）、通知伺服器、**鍵值儲存系統**（保存聊天紀錄）。

### 資料層

| 資料 | 選擇 | 原因 |
| --- | --- | --- |
| 使用者個人檔案、設定、朋友清單 | **關聯式資料庫** | 穩固可靠，可用複寫與分片擴展 |
| 聊天紀錄 | **鍵值儲存** | 理由見下列 |

選鍵值儲存的理由：

- 容易水平擴展，存取延遲低。
- 關聯式資料庫處理**長尾資料**不好；索引越大，隨機存取越慢。
- 聊天量巨大：Facebook Messenger 與 WhatsApp 每天處理 600 億則訊息。
- 近期訊息最常被讀取，但使用者仍可能隨機存取（搜尋、跳到被提及的訊息）。
- 一對一聊天讀寫比約 1:1。
- Facebook Messenger 用 HBase、Discord 用 Cassandra。

**訊息資料表：**

| 類型 | 主鍵 | 說明 |
| --- | --- | --- |
| 一對一 | `message_id` | 靠它排序；不能靠 `created_at`，因為兩則訊息可能同時建立 |
| 群組 | `(channel_id, message_id)` | `channel_id` 為分區鍵，因為群組內的查詢都在頻道內進行 |

**`message_id` 的要求**：唯一、可依時間排序。作法比較：

| 做法 | 評價 |
| --- | --- |
| MySQL `auto_increment` | NoSQL 通常不提供 |
| 全域 64 位元序列生成器（如 Snowflake） | 可行 |
| **局部序列號生成器** | 只要在群組內唯一、可排序即可；因為同一個頻道內的訊息才需要比較順序，實作更簡單 |

### 服務探索與訊息流程

**服務探索**（ZooKeeper）依地理位置、伺服器容量等推薦最佳聊天伺服器：

1. 使用者 A 嘗試登入，請求經負載平衡器到 API 伺服器。
2. 驗證後，服務探索挑選最佳聊天伺服器（如伺服器 2）並回傳給 A。
3. A 透過 WebSocket 連到伺服器 2。

**一對一訊息流程：**

1. A 把訊息送給聊天伺服器 1。
2. 伺服器 1 向 **ID 生成器**取得 `message_id`。
3. 訊息送進**訊息同步佇列**。
4. 訊息存入鍵值儲存。
5. 若 B 在線 → 轉發到 B 所連的聊天伺服器；若 B 離線 → 由推送通知伺服器送出通知。
6. 聊天伺服器 2 透過與 B 的 WebSocket 連線把訊息轉給 B。

### 多設備同步

每個設備維護自己的 `cur_max_message_id`，記錄該設備見過的最新訊息 ID。要同步的新訊息必須同時滿足：

- 接收者 ID 等於登入的使用者 ID。
- 鍵值儲存中的 `message_id` **大於**該設備的 `cur_max_message_id`。

由於每個設備各自有 `cur_max_message_id`，同步邏輯很簡單：各設備各自從儲存取最新訊息。

### 群組聊天

小型群組的作法：把訊息**複製**到每個群組成員的**訊息同步佇列**（可視為收件匣）。

| 優點 | 缺點 |
| --- | --- |
| 簡化同步，每個接收者只讀自己的收件匣 | 每個成員都存一份副本，群組大時成本高 |

這個設計適合小群組：微信（WeChat）用類似方式，並把群組限制在 500 人以內。大群組不一定適用。

### 連線狀態（presence）

| 事件 | 處理 |
| --- | --- |
| 登入 | 建立 WebSocket 後，狀態設為 `online`，記錄 `last_active_at` |
| 登出 | 狀態改成 `offline` |
| **斷線** | 不要一斷線就改成離線——使用者可能在隧道或不穩定網路中頻繁斷線再重連，狀態會一直閃爍。改用**心跳**：客戶端定期送心跳（書中例：每 5 秒）；超過門檻（例：30 秒）沒收到才標為離線 |

**狀態傳播：** 使用**發佈／訂閱**。使用者 A 的狀態變更時，發佈到頻道 A-B、A-C、A-D，由朋友 B、C、D 各自訂閱，透過 WebSocket 即時收到。小群組可行；大群組（如 10 萬人）每次狀態變更產生 10 萬個事件，代價太高，可改成只在使用者進入群組或手動重新整理時取得狀態。

### 可以接著聊

- 支援圖片、影片等媒體：壓縮、雲端儲存、縮圖。
- **端到端加密**（WhatsApp）：只有發送者與接收者可讀取。
- 客戶端快取，減少客戶端與伺服器間的資料傳輸。
- 縮短載入時間（Slack 用地理上分散的快取）。
- 聊天伺服器故障：服務探索給客戶端新伺服器重新建立連線。
- 訊息重發：在佇列中重新排隊、重試。

## 搜尋自動補全

要求：使用者在搜尋框輸入前綴時，**即時**回傳「最常被搜尋的前 k 個查詢」，所以也叫 typeahead、search-as-you-type。

### 需求與估算

| 項目 | 假設 |
| --- | --- |
| 比對 | 只比對查詢開頭 |
| 回傳 | 5 筆建議 |
| 排序依據 | 歷史查詢頻率 |
| 其他 | 不需要拼字檢查，英文小寫 |
| 延遲 | 約 **100 毫秒**內，否則會造成使用者感覺卡頓（書中引用 Facebook 文章） |
| DAU | 1,000 萬 |

估算：假設每人每天 10 次搜尋，每次搜尋平均輸入 20 個字元，而**每輸入一個字元就會送出一次查詢**（這是書中算式的假設）。

```text
QPS      = 10,000,000 × 10 次 × 20 字元 / 24 小時 / 3,600 秒 ≈ 24,000
峰值 QPS = 2 × QPS ≈ 48,000
新資料量 = 1,000 萬 × 10 次 × 20 byte × 20%（新查詢）≈ 0.4 GB／天
```

### 兩個服務

| 服務 | 職責 |
| --- | --- |
| 資料收集服務 | 收集使用者輸入的查詢並匯整（即時處理在大資料量下不切實際，但可作為起點） |
| 查詢服務 | 給前綴，回傳前 5 個最常被搜尋的查詢 |

基本版：頻率表 `(query, frequency)`，用 `LIKE 'prefix%' ORDER BY frequency DESC LIMIT 5` 查。資料少時可接受，資料大時資料庫會變瓶頸。

### Trie

**Trie**（前綴樹）是把大量字串壓縮儲存的樹狀結構：根代表空字串；每個節點存一個字元，並對應一個前綴或完整單詞。為了支援「按頻率排序」，節點上要再存頻率。

基本演算法取 top-k：找前綴節點 `O(p)` → 走訪子樹取得所有有效節點 `O(c)` → 排序取前 k `O(c log c)`，最壞要走完整棵樹。兩個最佳化：

| 最佳化 | 效果 |
| --- | --- |
| **限制前綴最大長度**（如 50） | 找前綴節點從 `O(p)` 變成 `O(小常數)` ≈ `O(1)` |
| **每個節點快取前 k 名查詢** | 取 top-k 從 `O(c + c log c)` 變成 `O(1)` |

代價是每個節點要多存 top-k 資料，**用空間換時間**，書中認為值得，因為回應速度至關重要。

```java
import java.util.*;

public class TrieTopKDemo {
    static final int K = 5;

    static class Node {
        final Map<Character, Node> children = new HashMap<>();
        // 每個節點快取「以此為前綴」的前 K 名查詢，查詢時不必走訪子樹
        final List<Map.Entry<String, Integer>> topK = new ArrayList<>();
    }

    private final Node root = new Node();

    /** 離線建 trie：沿路徑更新每個祖先節點的 topK */
    void insert(String query, int freq) {
        Node cur = root;
        update(cur, query, freq);
        for (char c : query.toCharArray()) {
            cur = cur.children.computeIfAbsent(c, x -> new Node());
            update(cur, query, freq);
        }
    }

    private void update(Node node, String query, int freq) {
        node.topK.removeIf(e -> e.getKey().equals(query));
        node.topK.add(Map.entry(query, freq));
        node.topK.sort((a, b) -> b.getValue() - a.getValue());
        if (node.topK.size() > K) node.topK.remove(node.topK.size() - 1);
    }

    List<String> suggest(String prefix) {
        Node cur = root;
        for (char c : prefix.toCharArray()) {
            cur = cur.children.get(c);
            if (cur == null) return List.of();
        }
        return cur.topK.stream().map(Map.Entry::getKey).toList();
    }

    public static void main(String[] args) {
        TrieTopKDemo trie = new TrieTopKDemo();
        Map.of("tree", 10, "true", 35, "toy", 14, "try", 29, "wish", 25, "win", 50)
                .forEach(trie::insert);
        System.out.println("tr -> " + trie.suggest("tr")); // [true, try, tree]
        System.out.println("t  -> " + trie.suggest("t"));  // [true, try, toy, tree]
        System.out.println("w  -> " + trie.suggest("w"));  // [win, wish]
    }
}
```

範例資料參考書中 trie 範例的頻率（`tree` 10、`true` 35、`try` 29、`wish` 25、`win` 50）；`toy` 的頻率是筆者自訂。實際系統是離線批次建 trie，不會在每次查詢時更新。

### 資料收集服務的重新設計

每天有數十億次查詢，若每次都即時更新 trie，查詢服務會被拖慢；而且 trie 建好後 top 建議不會頻繁變動。所以改成**離線**：

```text
Analytics 日誌 → 匯整器（每週等頻率） → 匯整後資料 → Worker 建 trie → Trie 資料庫 → Trie 快取
```

| 元件 | 說明 |
| --- | --- |
| Analytics 日誌 | 原始查詢資料，**只附加**、不建索引 |
| 匯整器 | 把日誌整理成 `(query, time, frequency)`；即時性要求高就縮短間隔（如 Twitter），否則每週一次也可能足夠 |
| Worker | 定期非同步工作，建 trie 後存入 trie 資料庫 |
| Trie 快取 | 分散式快取，把 trie 放在記憶體加速讀取，每週從資料庫取快照 |
| Trie 資料庫 | 持久化。選項：**文件儲存**（定期快照序列化，例如 MongoDB），或**鍵值儲存**（trie 每個前綴節點對應一個 key，節點資料對應 value） |

查詢流程：客戶端 → 負載平衡器 → API 伺服器 → 先取 trie 快取；沒有就從 trie 資料庫取並回填快取。

### 查詢服務最佳化

| 最佳化 | 說明 |
| --- | --- |
| **AJAX 請求** | Web 應用不需刷新整頁即可取得建議 |
| **瀏覽器快取** | 建議短時間內不太會變。Google 回應標頭有 `cache-control: private, max-age=3600`，快取一小時；`private` 表示只適用單一使用者，不能作為共用快取 |
| **資料取樣** | 大系統每筆查詢都記日誌太貴，可每 N 個請求只記 1 個 |

### trie 的建立、更新與刪除

| 操作 | 做法 |
| --- | --- |
| 建立 | worker 用匯整後的資料建立 |
| 更新 | 選項 1：**每週重建**，新 trie 取代舊的（推薦）。選項 2：直接更新節點——盡量避免，因為很慢；若 trie 很小才可接受。更新一個節點時，**所有祖先節點**也要一起更新，因為它們都存著 top-k |
| 刪除 | 仇恨、暴力、露骨或危險建議要移除。在 trie 快取前面加一層**篩選層**，依不同規則刪除；同時**非同步**刪除資料庫中的實際記錄，下一個更新週期就能用乾淨的資料建 trie |

### 擴展儲存

英文系統最單純的做法是**依第一個字元分片**：2 台就是 a–m、n–z；最多可分到 26 台（第一層分片）；還要更多可再依第二、三層切分，例如「s」開頭的可再分到 4 台。

問題是各字母開頭的單詞數量不一樣（例如「c」開頭遠多於「x」開頭）。書中的解法：分析歷史資料分佈，用**分片對應管理工具**維護查詢資料庫，決定每筆資料存在哪裡；例如若 `s` 的資料量與 `u–z` 加總接近，就可以用兩個分片，一個放 `s`，另一個放 `u–z`。

### 可以接著聊

| 問題 | 方向 |
| --- | --- |
| 支援多語言？ | trie 節點存 **Unicode** |
| 各國熱門查詢不同？ | 為不同國家建不同 trie，並放在 CDN 縮短回應 |
| 即時熱門趨勢（突發新聞）？ | 目前設計做不到：每週才更新、重建整棵 trie 又太久。方向有：用分片減少工作資料量、修改排名模型給近期查詢更高權重、資料以串流形式出現，需要串流處理系統（如 Hadoop MapReduce、Spark Streaming、Storm、Kafka） |
