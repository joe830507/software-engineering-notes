# 擴展與粗略估算

> 對應《系統設計面試指南》第 1、2 章。這一頁是所有案例的共同底層：幾乎每個案例都會重複用到「無狀態 Web 層、快取、CDN、複寫、分片、訊息佇列」。

## 從單一伺服器到百萬使用者

擴展是**反覆迭代**的過程：每次出現瓶頸，就拆開一個元件讓它能獨立擴展。

### 演進路徑

| 階段 | 做法 | 解決什麼 | 帶來什麼新問題 |
| --- | --- | --- | --- |
| 1. 單一伺服器 | Web、資料庫、快取都在一台 | 最簡單 | 容量與故障風險全擠在一起 |
| 2. 拆 Web 層與資料層 | 資料庫獨立成伺服器 | 兩層可各自擴展 | 要選資料庫類型 |
| 3. 負載平衡器 | 流量先到 LB，LB 以內網 IP 轉給多台 Web | Web 層故障轉移、容量 | 有狀態的 Web 伺服器很難加減 |
| 4. 資料庫複寫 | 主資料庫寫入、從資料庫讀取 | 讀多寫少的效能、可用性 | 主庫掛掉要升級從庫，資料可能落後 |
| 5. 快取層 | 常讀、少改的資料放記憶體 | 降低資料庫負載、縮短回應 | 一致性、過期、逐出 |
| 6. CDN | 靜態資源放在地理分散的節點 | 縮短遠距離載入 | 成本、失效、CDN 故障退守 |
| 7. 無狀態 Web 層 | session 移到共用儲存 | 可自動擴展 | 共用儲存要夠可靠 |
| 8. 多資料中心 | geoDNS 導向最近的資料中心 | 全球延遲、災難容錯 | 流量導向、資料同步、部署一致 |
| 9. 訊息佇列 | 生產者與消費者解耦 | 各部分獨立擴展、緩衝 | 要處理重試與重複 |
| 10. 日誌、指標、自動化 | 集中日誌、監控、CI/CD | 看得見、管得動 | 需要投入工具 |
| 11. 資料庫分片 | 以分片鍵把資料分到多個資料庫 | 單庫容量與寫入上限 | 重新分片、熱點、跨分片 JOIN |

### 關鍵元件的細節

**資料庫類型。** 多數開發者預設用關聯式資料庫，因為它已被驗證超過 40 年。下列情況可考慮 NoSQL：

- 需要超低延遲。
- 資料非結構化，或沒有關聯。
- 只需要序列化與反序列化（JSON、XML、YAML）。
- 要儲存大量資料。

NoSQL 分為四類：鍵值、圖、欄、文件；通常不支援 JOIN。

**垂直 vs 水平擴展。**

| | 垂直（scale up） | 水平（scale out） |
| --- | --- | --- |
| 做法 | 加 CPU、記憶體 | 加伺服器 |
| 優點 | 簡單 | 沒有硬體上限、可冗餘 |
| 缺點 | 有硬體上限、沒有故障轉移 | 要處理分散式問題 |

**負載平衡器與複寫的故障處理。**

- Web 伺服器 #1 離線：流量導向 #2，並可加入新伺服器。
- 只有一台從庫且離線：讀取暫時導向主庫，之後補上新從庫；有多台從庫則轉到其他從庫。
- 主庫離線：把一台從庫升為新主庫。實務上更複雜，因為從庫可能不是最新資料，需要資料復原腳本。

**快取的五個注意事項。**

| 項目 | 重點 |
| --- | --- |
| 何時用 | 讀取頻繁、修改不頻繁的資料；快取在記憶體，重要資料仍要放持久儲存 |
| 過期策略 | 不要太短（頻繁回源）也不要太長（資料過舊） |
| 一致性 | 儲存與快取不是同一次操作更新，可能不一致；跨區域更困難 |
| 減輕故障 | 單一快取是單點故障（SPOF），應跨資料中心多台，並多配一些記憶體 |
| 逐出策略 | 常見 LRU，也有 LFU、FIFO |

書中示範的是 **read-through** 型態：先查快取，沒有再查資料庫並寫回快取。

**CDN 的注意事項。**

- 成本：資料進出 CDN 都收費，很少用的內容放 CDN 沒有效益。
- 過期時間：內容時效敏感就要設短，但太短會頻繁回源。
- 退守：CDN 出問題時，客戶端要能改向來源取資源。
- 失效：用 CDN 供應商的 API 讓物件失效，或在 URL 加版本，例如 `image.png?v=2`。

**有狀態 vs 無狀態。** 有狀態伺服器在請求之間記住客戶端資料，同一使用者的請求必須回到同一台，sticky session 能做到，但加減伺服器與處理故障都更困難。無狀態架構把狀態放在共用儲存（關聯式資料庫、Redis／Memcached、NoSQL），任何伺服器都能處理任何請求，因此可以依流量自動加減。

**多資料中心的三個挑戰。**

| 挑戰 | 做法 |
| --- | --- |
| 流量重定向 | geoDNS 依使用者位置解析到最近的資料中心；故障時全導向正常的那個 |
| 資料同步 | 跨資料中心複製資料；書中提到 Netflix 的非同步複製 |
| 測試與部署 | 各地都要測，自動化部署確保每個資料中心一致 |

**資料庫分片。**

```text
user_id % 4 → 分片
0 → 分片 #0    1 → 分片 #1    2 → 分片 #2    3 → 分片 #3
```

分片鍵（sharding key）決定查詢能否直接導向正確的資料庫，選擇時最重要的標準是**資料能均勻分散**。分片帶來三個挑戰：

| 挑戰 | 說明 | 常見處理 |
| --- | --- | --- |
| 重新分片 | 資料成長超出單一分片，或分佈不均使某分片先滿 | 一致性雜湊（見「基礎元件」） |
| 名人問題（熱點） | 名人資料集中在同一分片，被大量讀取壓垮 | 為名人單獨分配分片，必要時再細分 |
| JOIN 與去正規化 | 跨分片 JOIN 很困難 | 去正規化，讓查詢在單表完成 |

### 百萬使用者的檢查清單

- Web 層保持**無狀態**。
- 每一層都有**冗餘**。
- 盡可能**快取**資料。
- 靜態資料放 **CDN**。
- 多資料中心。
- 用**訊息佇列**拆開元件。
- 各層切成獨立服務。
- 監控並自動化。
- 資料層用**分片**擴展。

## 粗略估算

估算的目的是用思維實驗加上幾個常用數字，判斷設計方向是否可行。**過程比結果更重要**：面試官看的是你怎麼解題。

### 2 的次方

| 次方 | 近似值 | 全名 | 縮寫 |
| --- | --- | --- | --- |
| 10 | 一千 | Kilobyte | KB |
| 20 | 一百萬 | Megabyte | MB |
| 30 | 十億 | Gigabyte | GB |
| 40 | 一兆 | Terabyte | TB |
| 50 | 一千兆 | Petabyte | PB |

1 byte = 8 bits，一個 ASCII 字元佔 1 byte。

### 每位工程師都該知道的延遲數字

來自 Jeff Dean 2010 年的數據，部分數字已過時，但可以顯示操作的相對快慢：

| 操作 | 時間 |
| --- | --- |
| L1 快取參照 | 0.5 ns |
| L2 快取參照 | 7 ns |
| 互斥鎖鎖定／解鎖 | 100 ns |
| 主記憶體參照 | 100 ns |
| 壓縮 1 KB | 10 µs |
| 1 Gbps 網路傳送 2 KB | 20 µs |
| 記憶體循序讀 1 MB | 250 µs |
| 同資料中心往返 | 500 µs |
| 磁碟搜尋 | 10 ms |
| 網路循序讀 1 MB | 10 ms |
| 磁碟循序讀 1 MB | 30 ms |
| 封包從加州到荷蘭再回來 | 150 ms |

由此得到的結論：

- 記憶體快、磁碟慢，盡量避免磁碟搜尋。
- 簡單壓縮很快，傳網路前盡量先壓縮。
- 資料中心通常在不同地區，彼此傳資料需要時間。

### 可用性與停機時間

可用性用「幾個 9」衡量，主流雲端供應商的 SLA 多在 99.9% 以上。

| 可用性 | 每天 | 每週 | 每月 | 每年 |
| --- | --- | --- | --- | --- |
| 99% | 14.40 分 | 1.68 小時 | 7.31 小時 | 3.65 天 |
| 99.9% | 1.44 分 | 10.08 分 | 43.83 分 | 8.77 小時 |
| 99.99% | 8.64 秒 | 1.01 分 | 4.38 分 | 52.60 分 |
| 99.999% | 864 毫秒 | 6.05 秒 | 26.30 秒 | 5.26 分 |

### 範例：推文系統的 QPS 與儲存

假設（書中標明這不是 Twitter 真實數字）：每月 3 億活躍使用者，50% 每天使用，每人每天發 2 則，10% 含媒體，媒體 1 MB。

```text
DAU        = 3 億 × 50% = 1.5 億
推文 QPS   = 1.5 億 × 2 / 24 / 3600 ≈ 3,500
峰值 QPS   = 2 × QPS ≈ 7,000
每日媒體   = 1.5 億 × 2 × 10% × 1 MB ≈ 30 TB
五年媒體   = 30 TB × 365 × 5 ≈ 55 PB
```

### 估算的技巧

| 技巧 | 說明 |
| --- | --- |
| 近似與捨入 | `99987 / 9.1` 直接當 `100000 / 10`；不用在精確度上花時間 |
| 寫下假設 | 之後回頭對照，也讓面試官確認 |
| 標單位 | 寫 `5 MB`，不要只寫 `5` |
| 常見題目 | QPS、峰值 QPS、儲存空間、快取大小、伺服器數量 |

QPS 的通用算法是：`總請求數 / 一天秒數（86,400）`，峰值通常取平均的兩倍（書中的慣例，不是定律）。
