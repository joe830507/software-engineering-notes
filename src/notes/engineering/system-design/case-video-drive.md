# 案例：YouTube 與 Google Drive

> 對應《系統設計面試指南》第 14、15 章與第 16 章「持續學習」。兩題都以**大檔案**為核心：影片重點在轉碼與分發，雲端硬碟重點在分塊、同步與一致性。最後附一張跨案例的技術速查表。

## 設計 YouTube（影片串流）

### 需求與估算

書中引用的 YouTube 規模（2020 年）：每月 20 億活躍使用者、每天觀看 50 億支影片。面試中範圍縮小到：

- 重點功能：**上傳影片、觀看影片**。
- 客戶端：行動 App、Web 瀏覽器、智慧型電視。
- 全球使用者；支援多數解析度與格式；需要加密；影片大小上限 1 GB 以內（中小型影片為主）。
- 可以善用雲端服務（BLOB 儲存、CDN），不必從頭自建。

估算（均為假設）：

```text
DAU 500 萬，每人每天看 5 支影片，10% 的使用者每天上傳 1 支，平均 300 MB
每日新增儲存 = 500 萬 × 10% × 300 MB = 150 TB
CDN 成本     = 500 萬 × 5 支 × 0.3 GB × 0.02 美元/GB = 每天 150,000 美元
```

CDN 成本非常高，就算雲端供應商給大客戶折扣也一樣，所以後面要談降低成本。

### 為什麼不全部自己做

- 面試目標是「選對技術」，不是解釋 BLOB 儲存系統或 CDN 的內部。
- 自建可擴展的 BLOB 儲存與 CDN 又複雜又昂貴；Netflix 用 Amazon 雲端服務，Facebook 用 Akamai CDN。

### 高階設計

三大部分：**客戶端**、**CDN**（影片全部儲存在這裡並由它串流）、**API 伺服器**（除了串流以外的一切：推薦、產生上傳網址、更新 metadata、註冊登入）。

**影片上傳**由兩個**平行**流程組成：

```text
流程 A：上傳影片本體
  使用者 → 原始儲存（BLOB）→ 轉碼伺服器
  轉碼完成後，平行兩路：
    (a) 已轉碼儲存 → CDN
    (b) 完成事件佇列 → 完成事件處理程序 → 更新 metadata 資料庫與快取
  最後由 API 伺服器通知客戶端「已上傳」

流程 B：更新 metadata（檔名、大小、格式等）
  使用者 → API 伺服器 → metadata 快取與資料庫
```

| 元件 | 用途 |
| --- | --- |
| 原始儲存系統 | BLOB 儲存，保存原始影片 |
| 轉碼伺服器 | 把影片轉成不同格式與位元率，適應不同設備與頻寬 |
| 已轉碼儲存 | 保存轉碼後的檔案 |
| 完成事件佇列／處理程序 | 轉碼完成後，更新 metadata 資料庫與快取 |
| metadata 資料庫與快取 | 影片資訊，分片與複寫以滿足效能與可用性 |

**影片串流**：串流是邊下載邊播放，不用等整支下載完。使用者從離自己最近的 **CDN 邊緣伺服器**取得內容，延遲幾乎不存在。串流協定控制資料如何傳輸，常見的有：

| 協定 | 備註 |
| --- | --- |
| MPEG-DASH | 透過 HTTP 的動態自適應串流 |
| Apple HLS | HTTP Live Streaming |
| Microsoft Smooth Streaming | |
| Adobe HDS | HTTP Dynamic Streaming |

不同協定支援不同的影片編碼與播放器，要依實際使用情境選擇；不需要背協定細節。

### 深入：影片轉碼

**為什麼要轉碼**：

- 原始影片很大：60 fps 的一小時高畫質影片可能佔數百 GB。
- 許多設備與瀏覽器只支援特定格式。
- 要讓高頻寬使用者看高畫質，低頻寬使用者看低畫質。
- 網路隨時變化（尤其行動裝置），播放時可自動或手動切換品質。

編碼格式有兩部分：**容器**（把影片、聲音、metadata 放一起，如 `.avi`、`.mov`、`.mp4`）與 **codec**（壓縮／解壓縮演算法，如 H.264、VP9、HEVC）。

**DAG 模型。** 不同創作者有不同需求（加浮水印、自訂縮圖、只提供高畫質），轉碼又是耗運算的工作。為了彈性與平行性，借鏡 Facebook 的串流影片引擎，用**有向無環圖（DAG）**定義任務，任務可依序或平行執行。原始影片會被拆成**影片、聲音、metadata**，可套用的任務包括檢查（品質與格式錯誤）、影片編碼（多種解析度與 codec）、縮圖、浮水印。

**轉碼架構的元件：**

| 元件 | 職責 |
| --- | --- |
| **預處理器** | 把影片依 **GOP**（一組連續畫面）對齊切成小段，舊版客戶端不能切時由它代勞；產生 DAG；把 GOP 與 metadata 存進暫存儲存以便失敗重試 |
| **DAG 排程器** | 把 DAG 切成多階段任務，放入資源管理工具的任務佇列 |
| **資源管理工具** | 有三個佇列：**任務佇列**（依優先權）、**工作者佇列**（依利用率）、**執行佇列**（目前執行中的任務與工作者）；任務排程器選出最佳的任務／工作者配對，指派執行，完成後從執行佇列移除 |
| **任務工作者** | 執行 DAG 定義的任務；不同工作者可以專責不同任務（如縮圖、編碼） |
| **暫存儲存** | 依資料類型、大小、存取頻率、有效壽命選擇：metadata 常被存取且很小，放記憶體；影片與聲音放 BLOB |
| **已編碼影片** | 最終輸出，推送到 CDN |

### 系統最佳化

| 面向 | 做法 |
| --- | --- |
| **速度：平行上傳** | 把影片依 GOP 切成小塊，由客戶端並行上傳；一塊失敗也能快速重試，不必整支重傳 |
| **速度：上傳中心** | 全球多個上傳中心（用 CDN 當上傳中心），使用者就近上傳 |
| **速度：全程平行** | 以訊息佇列解耦各模組，下載、編碼、上傳可以各自平行 |
| **安全：預簽名網址** | 客戶端先向 API 伺服器請求**預簽名網址**，再用它直接把影片上傳到指定位置。這是 Amazon S3 的術語，Azure 稱為「共享存取簽名」 |
| **安全：保護版權** | **DRM**（Apple FairPlay、Google Widevine、Microsoft PlayReady）、**AES 加密**加授權策略、**視覺浮水印** |
| **成本** | 影片觀看量符合**長尾分佈**：少數影片被大量觀看，多數很少人看。因此：(1) 只有最熱門的影片放 **CDN**，其餘由自家高容量影片伺服器提供；(2) 不熱門的內容不必保存很多編碼版本，短片可依實際觀看情況按需編碼；(3) 只在特定地區熱門的影片不必分配到其他地區；(4) 大型串流公司可自建 CDN 並與 ISP 合作，降低頻寬費用。最佳化前要先分析內容熱度、存取模式與影片大小 |

### 錯誤處理

錯誤分兩類：**可恢復**（例如某段轉碼失敗）通常重試幾次即可；**不可恢復**（例如影片格式錯誤）則停止並回傳錯誤碼。

| 元件 | 處理 |
| --- | --- |
| 上傳錯誤 | 重試 |
| 影片切分錯誤 | 舊客戶端不支援 GOP 對齊時，由伺服器切分 |
| 預處理器錯誤 | 重新產生 DAG |
| DAG 排程器錯誤 | 任務重新排程 |
| 資源管理工具佇列問題 | 使用副本 |
| 任務工作者故障 | 改用新的工作者重試 |
| API 伺服器 | 無狀態，由負載平衡器導向其他 API 伺服器 |
| metadata 快取 | 多副本，一個故障仍有其他節點可用 |
| metadata 資料庫 | master 故障就提升一台 slave；slave 故障就改用另一台並補新的 |

### 可以接著聊

- 擴展 API 層（無狀態）、擴展資料庫（複寫與分片）。
- **直播**：延遲要求更高，可能要不同的串流協定，而且錯誤處理不同——耗時太久的任務要略過。
- **影片下架**：侵權、色情或其他非法影片，上傳時的審核與使用者舉報後處理。

## 設計 Google Drive（檔案同步儲存）

### 需求與估算

| 項目 | 假設 |
| --- | --- |
| 核心功能 | 上傳與下載檔案、**跨多設備同步**、查看檔案修訂歷史、與朋友分享、檔案被編輯／刪除／分享時**發通知** |
| 不討論 | Google 文件的多人同時編輯 |
| 檔案 | 任何類型、必須**加密**、單檔上限 **10 GB** |
| 規模 | 5,000 萬註冊使用者、**1,000 萬 DAU** |
| 空間 | 每人 10 GB，總共 5,000 萬 × 10 GB = **500 PB** |
| 上傳 | 每人每天 2 次、平均檔案 500 KB → QPS ≈ 1,000 萬 × 2 / 86,400 ≈ **240**，峰值 480 |

非功能需求：**可靠性**（資料遺失不可接受）、**同步速度快**、**頻寬使用低**（行動網路流量有限）、可擴展、高可用。

### 從單一伺服器演進

書中採「先簡單、再擴大」的敘事：

| 階段 | 做法 |
| --- | --- |
| 1. 單一伺服器 | Web 伺服器 + 資料庫（metadata）+ 1 TB 儲存，用目錄表示**名稱空間** |
| 2. 儲存快滿 | 依 `user_id` 對資料**分片**到多台儲存伺服器，但仍有伺服器故障造成資料遺失的風險 |
| 3. 改用 **Amazon S3** | 物件儲存，**同區域與跨區域複製**，可冗餘、防遺失 |
| 4. 其他改進 | 加負載平衡器與多台 Web 伺服器；**metadata 資料庫**移出伺服器並複寫、分片；檔案放 S3 |

**同步衝突。** 兩位使用者同時修改同一檔案時，**先被處理的版本勝出**，後到的使用者會收到衝突通知，兩個版本（本地副本與伺服器上的最新版本）都顯示，使用者可選擇合併或用某版覆蓋。

### API

三類：上傳（簡單上傳、**斷點續傳**）、下載、取得修訂歷史。**斷點續傳**適用大檔案與網路不穩的情況，三步驟：取得續傳網址 → 上傳並監控狀態 → 中斷後從斷點續傳。所有 API 都要驗證身份，並使用 HTTPS（SSL）。

### 高階元件

| 元件 | 說明 |
| --- | --- |
| 使用者 | 瀏覽器或行動 App |
| **區塊伺服器** | 把檔案切成**區塊**，壓縮、加密後上傳到雲端儲存；每個區塊有唯一雜湊值，記在 metadata 資料庫。Dropbox 的區塊最大 **4 MB** |
| 雲端儲存系統 | 區塊以獨立物件存放（S3） |
| 冷儲存 | 存放長期不活躍的資料 |
| 負載平衡器、API 伺服器 | API 伺服器負責上傳流程以外的所有事：驗證身份、使用者資料、更新 metadata |
| metadata 資料庫、快取 | 使用者、檔案、區塊、版本等 metadata（**不存檔案本體**） |
| **通知服務** | 發佈／訂閱，檔案新增、編輯、刪除時通知相關客戶端 |
| **離線備份佇列** | 客戶端離線時先存著資訊，之後上線再同步 |

### 深入設計

**區塊伺服器與頻寬節省。** 兩個最佳化：

- **差異同步（delta sync）**：檔案修改後只傳**有變動的區塊**（例如區塊 2 與 5 變動就只傳這兩個），不重傳整個檔案。
- **壓縮**：依檔案類型用不同演算法（文字用 gzip、bzip2，圖片與影片需要專用演算法）。

區塊上傳流程：切分 → 壓縮 → 加密 → 上傳到雲端儲存。

**強一致性。** 書中要求 metadata 的讀取反映最新已完成的更新，並選用關聯式資料庫。這不代表離線客戶端會立即同步；客戶端仍需重新連線並取得更新。

**實作限制（補充原書的簡化說法）：**

- **更新資料庫後刪除快取，不足以保證強一致。** 例如讀取端先讀到舊版 v1，寫入端更新為 v2 並刪除快取，讀取端最後又把 v1 填回快取，後續請求就會讀到舊值。
- 要求強一致的 metadata 讀取可直接走**提供所需一致性保證的權威資料庫路徑**，避免讀取落後副本。若要使用快取，須建立完整的版本驗證或讀寫協調協定，涵蓋填回、失效、並行操作與故障；僅加 TTL 或延遲雙刪不能構成嚴格保證。
- **ACID 的 C 與分散式讀寫的一致性不是同一概念**，不能由「支援 ACID」直接推導所有讀取都看到最新值。應確認交易隔離、複寫與讀取設定；NoSQL 是否提供強一致也取決於具體系統及操作，不能一概而論。

**metadata 資料庫的表**：

| 表 | 內容 |
| --- | --- |
| `user` | 使用者基本資料 |
| `device` | 設備資訊（一個使用者可有多個設備） |
| `namespace` | 使用者的根目錄 |
| `file` | 最新檔案資訊 |
| `file_version` | 版本歷史，每筆**唯讀**以維持修訂記錄完整 |
| `block` | 檔案區塊資訊，依序連結所有區塊即可重建任何版本的檔案 |

**上傳流程**：客戶端同時送出兩個請求——(1) **新增 metadata**（檔案狀態先是 `pending`，通知相關客戶端「有檔案正在上傳」）；(2) **上傳檔案到雲端儲存**（經區塊伺服器）。上傳完成後，雲端儲存觸發回呼，通知 API 伺服器把狀態改成 `uploaded`，並通知相關客戶端。

**下載流程**：檔案被新增或編輯時，通知服務通知其他客戶端；客戶端取得變更後先向 API 伺服器取得最新 metadata，再從區塊伺服器下載區塊並重建檔案。

**通知服務。** 兩種選擇：

| 方式 | 適合 |
| --- | --- |
| **長輪詢**（Dropbox 的做法） | 檔案變更通知是**單向**（伺服器 → 客戶端），不會突發大量資料 |
| WebSocket | 雙向即時通訊（例如聊天） |

書中選**長輪詢**：每個客戶端與通知服務維持一條長輪詢連線，偵測到檔案變動就關閉該連線，客戶端再向 metadata 伺服器取最新內容；收到回應或逾時後重新建立連線。

### 節省儲存空間

| 做法 | 說明 |
| --- | --- |
| **去重複區塊** | 在帳號層級，雜湊值相同的區塊視為重複，只存一份 |
| **智慧備份策略** | 限制保存的版本數量（超過時用新版取代最舊的）；只保留有價值的版本，頻繁編輯的檔案不必保存上千個版本，給近期版本較高權重 |
| **冷資料移到冷儲存** | 數月或數年沒用的資料，放 Amazon S3 Glacier 這類比 S3 便宜很多的儲存 |

### 故障處理

| 元件 | 處理 |
| --- | --- |
| 負載平衡器 | 有第二台接手，彼此以心跳互相監控 |
| 區塊伺服器 | 其他伺服器接手未完成或待處理的工作 |
| 雲端儲存 | S3 跨區域複製，從其他區域取檔 |
| API 伺服器 | 無狀態，負載平衡器改導其他伺服器 |
| metadata 快取 | 多副本；故障後以新的替換 |
| metadata 資料庫 | master 故障就升級一台 slave 並新增 slave；slave 故障就用另一台讀取並補新機器 |
| 通知服務 | 每台伺服器維持超過百萬連線（Dropbox 2012 年演講的數字），故障時所有長輪詢連線消失，客戶端要重新連線；一次讓大量連線重新上線很慢 |
| 離線備份佇列 | 多副本；故障後使用者要重新訂閱 |

### 設計選擇的取捨

- **客戶端直傳雲端儲存**，繞過區塊伺服器：上傳更快，但分塊、壓縮、加密邏輯要在 iOS、Android、Web 各實作一次，容易出錯；客戶端也容易被入侵，不適合放加密邏輯。書中選擇把邏輯集中在區塊伺服器。
- 把**線上／離線狀態邏輯**拆成獨立的連線狀態服務，從通知服務移出，更容易被其他服務整合。

## 跨案例技術速查

| 問題 | 常用技術 | 出現在 |
| --- | --- | --- |
| 單機撐不住，要水平擴展 | 無狀態服務 + 負載平衡器 | 幾乎所有案例 |
| 讀多寫少、要快 | 快取（read-through）、CDN、讀寫分離 | 短網址、動態訊息、自動補全 |
| 資料太大要分散 | 分片、一致性雜湊 | KV 儲存、聊天、爬蟲下載器 |
| 兩個元件耦合、處理有尖峰 | 訊息佇列 + worker | 通知、動態訊息扇出、YouTube 轉碼 |
| 不能丟、可能重複 | 日誌 + 重試 + 以 ID 去重 | 通知、聊天 |
| 需要全域唯一、可排序的 ID | Snowflake、局部序列號 | 短網址、聊天 `message_id` |
| 要判斷「看過了嗎」 | Bloom 篩選器、雜湊表 | 爬蟲、短網址衝突檢查 |
| 即時推送給使用者 | WebSocket、長輪詢 | 聊天、Drive 通知 |
| 大檔案傳輸 | 分塊、差異同步、預簽名網址、平行上傳 | YouTube、Drive |
| 過熱資料 | 混合推拉、單獨分片、熱門快取 | 動態訊息的名人問題 |
| 要同時保證可用與一致 | 取捨 CAP、quorum、向量時鐘 | KV 儲存、Drive metadata |

## 持續學習（第 16 章）

書中的建議：除了熟悉自己的技術之外，也要多讀真實系統的架構文章（Facebook、Netflix、Twitter、Uber、Dropbox、WhatsApp 等）和各大公司的工程部落格，理解每項技術解決的問題，並留意共通的原則。面試前先讀目標公司的工程部落格，通常能了解他們使用的技術與系統。
