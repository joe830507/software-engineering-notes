# 架構風格與選擇

> 對應《軟體架構原理》Part II：架構風格（第 9–18 章）。書中對每種風格都用同一組問題描述：**拓撲、優缺點、量子數量、適合的情境**，並以「特性等級」表比較。OCR 稿中星號等級圖無法辨識，下面的比較以**正文說明**為準。

## 一覽表

| 風格 | 分割方式 | 量子 | 一句話 |
| --- | --- | --- | --- |
| **分層** | 技術 | 1 | 簡單、便宜，但部署、測試、擴展差 |
| **管道（pipeline）** | 技術 | 1 | 資料經過一連串篩選器處理，單向流動 |
| **微核心** | 技術／領域 | 1 | 核心系統 + 外掛，易擴充 |
| **服務式** | 領域 | 1 到多 | 粗粒度領域服務 + 共用資料庫，微服務的務實替代 |
| **事件驅動** | 技術 | 1 到多 | 非同步事件處理，高效能、高擴展 |
| **空間式** | 技術 | 多 | 以記憶體資料格網取代資料庫，極致彈性 |
| **協作驅動的服務導向（SOA）** | 技術 | 1 | 企業服務匯流排，重用導向，已不流行 |
| **微服務** | 領域 | 多 | 極端解耦、每個服務自有資料，擴展與演進佳，效能與成本要付代價 |

## 分層架構

**拓撲。** 最常見的風格。程式碼依技術能力分成**水平層**，典型四層：展示層、業務層、持久層、資料庫層（持久層與資料庫有時合併為三層）。

| 概念 | 說明 |
| --- | --- |
| **封閉層** | 請求必須依序經過每一層，不能跳過 |
| **開放層** | 請求可以跳過這一層 |
| **隔離層** | 一層的改變通常不影響其他層，前提是層與層之間的合約不變；開放層會破壞隔離 |

> 封閉層能促成隔離層，但並非所有請求都值得走完整流程（例如簡單查詢）；因此要判斷哪些層可以設計為**開放**，並記錄決策。

**注意事項：**

- **架構汙水池反模式**：請求通過各層卻幾乎沒有任何處理，只是單純傳遞。書中的 **80-20 法則**：若只有約 20% 的請求符合汙水池特徵，還可接受；若約 80% 的請求都符合，就表示分層架構不適用於這個問題。
- 沒有分層邊界治理，容易失控成**大泥球**（big ball of mud）。

**特性：**

| 強項 | 弱項 |
| --- | --- |
| **整體成本與簡單性**：單體、容易理解、容易建置維護 | **部署性與測試性低**：一行改動要重新部署整個單元，風險高、頻率低 |
| 可靠度中等 | **彈性與可擴展性低**：只有一個量子；可以用快取、多執行緒等技巧撐，但有上限 |
| | **效能中低**：封閉層與缺乏平行處理 |
| | **容錯差**：記憶體不足會讓整個應用掛掉，平均恢復時間長 |

**適合：** 小型、簡單的應用；預算與時程有限；還不確定要用什麼架構的**起點**。也是規劃好的模組化單體的常見起點。

## 管道架構

**拓撲。** 由**管道（pipe）**與**篩選器（filter）**組成，資料單向流動：

| 篩選器類型 | 角色 |
| --- | --- |
| 生產者（producer／source） | 起點，只輸出 |
| 轉換者（transformer） | 接收輸入，轉換後輸出 |
| 測試者（tester） | 依條件決定資料是否繼續往下傳 |
| 消費者（consumer） | 終點，只輸入（例如寫入資料庫或畫面） |

書中例子：Kafka 的服務遙測資料 → 服務資訊記錄（生產者）→ 持續期間篩選器（測試者）→ 持續期間計算器（轉換者）／上線時間篩選器 → 上線時間計算器 → 資料庫輸出（消費者）。

每個篩選器**只做一件事**、彼此獨立，所以容易擴充（加一個新篩選器即可）；Unix 的 `|` 組合命令、ETL、許多轉換流程都是這種架構。

## 微核心架構

**拓撲。** 一個**核心系統**加上多個**外掛元件**：

- 核心只含**最小功能**（通用、穩定的流程）。
- 外掛含客製、專屬、易變的邏輯，彼此**獨立**，只與核心通訊。

適合需要大量客製或產品化的系統：像 IDE 與瀏覽器那樣靠外掛擴充的產品，或依客戶、地區而有不同規則的商業軟體（筆者補充的例子，非逐字出自書中）。

| 特性 | 說明 |
| --- | --- |
| 優點 | 簡單、成本低、可演進性好（加外掛不動核心）、可測試 |
| 缺點 | 外掛過多或外掛間需要溝通時變複雜；整體可擴展性、容錯不高 |

## 服務式架構

**拓撲。** 微服務與分層之間的**務實折衷**，是分散式架構但沒有微服務那麼複雜與昂貴：

- **使用者介面**（單一或依領域拆分）。
- **粗粒度的領域服務**：每個服務對應一個領域（如訂單、客戶、報價），獨立部署。書中說典型為 **4 到 12 個**服務，平均約 **7 個**。
- **單一共用資料庫**（也可以依領域拆成幾個）。
- 可選的 API 層（代理或閘道）。

服務之間**通常不互相呼叫**，由使用者介面或 API 層協調；服務內部可以是分層或領域分割。

| 優點 | 缺點 |
| --- | --- |
| 部署與測試比單體好：變更只影響單一服務 | 共用資料庫：資料庫變更要協調多個服務，是主要的耦合點 |
| 容錯：一個服務掛了其他仍可運作 | 粗粒度：不像微服務可以細緻擴展 |
| 成本與複雜度比微服務低，很多商業應用的合理選擇 | 效能中等 |

## 事件驅動架構

**特性：** 以**非同步**事件處理系統，高效能、高擴展、高彈性，但複雜度高（錯誤處理、一致性、測試）。有兩種拓撲：

| | 代理者（broker）拓撲 | 調停者（mediator）拓撲 |
| --- | --- | --- |
| 控制 | **沒有中央調停者**；事件處理器透過事件代理者（RabbitMQ、ActiveMQ 等）串成鏈，各自處理後發出新事件 | 有**事件調停者**，掌握整個流程的步驟與錯誤處理 |
| 優點 | 高度解耦、效能與擴展極高 | 流程控制、錯誤處理與重新啟動比較容易 |
| 缺點 | 流程分散，不容易掌握整體狀態；出錯難以恢復 | 調停者可能成為瓶頸；耦合較高 |
| 適合 | 事件處理相對簡單、不需要中央協調 | 有多步驟、有順序、需要協調的工作流程 |

書中討論的事件驅動主題：

| 主題 | 說明 |
| --- | --- |
| **錯誤處理** | 非同步下，一個處理器失敗不會讓呼叫方知道；常用工作流程事件模式，把失敗事件交給專門處理器 |
| **避免資料遺失** | 訊息可能在傳送、處理、儲存階段消失；用持久化佇列、確認、同步寫入 |
| **廣播能力** | 事件可以被多個處理器各自訂閱，不需發送方知道 |
| **請求與回覆** | 非同步中也有需要回應的情況，用相關 ID 與回覆佇列 |
| **請求式 vs 事件式** | 請求式：發送方**指揮**，要確定性回應（如查詢）；事件式：發送方**通知**，彈性高。要依問題選擇 |
| **混合式** | 事件驅動常和其他架構混合，例如微服務間用事件通訊 |

## 空間式架構

針對**高並行與高彈性**（例如票務系統、線上拍賣），把**資料庫從同步交易路徑中拿掉**：

| 元件 | 說明 |
| --- | --- |
| **處理單元** | 應用程式碼 + **記憶體內資料格網**，可以依負載動態啟動／關閉 |
| **虛擬化中介軟體** | 負責管理與協調：**訊息格網**（分派請求）、**資料格網**（同步處理單元間資料）、**處理格網**（協調多個處理單元）、**部署管理員**（依負載啟動與關閉處理單元） |
| **資料幫浦** | 非同步把資料更新送往資料庫 |
| **資料寫入器**、**資料讀取器** | 寫入器接收幫浦訊息更新資料庫；讀取器在處理單元啟動時載入資料到快取 |

**複製快取 vs 分散式快取**：複製快取每個單元都有完整資料，速度快但資料量受限；分散式快取靠中央控管，資料量大但較慢。這種風格擴展極佳，但**複雜、昂貴、不易測試**。

## 協作驅動的服務導向架構（SOA）

2000 年代的企業架構。以**企業服務匯流排（ESB）**作為編排與協作的中心，分成業務服務、企業服務、應用服務、基礎設施服務等層級，目標是**最大化重用**。

書中的評價：這是**技術分割最極端**的架構，一個業務變更要碰很多服務；因為偏重重用，**耦合極高**；整體只有**一個量子**。當時敏捷與工程實務還沒有興起，所以對部署、測試等特性的支援很差。這種架構的缺點直接催生了微服務。

## 微服務架構

**拓撲。** 許多**小而獨立**的服務，每個服務通常有自己的資料庫，以**限界上下文（bounded context）**劃分：**每個服務邊界對應一個領域或工作流程**，且追求極端解耦。

| 面向 | 說明 |
| --- | --- |
| **粒度** | 太細會造成服務間通訊過多，太粗又失去微服務的好處；可用「服務是否代表單一目的」「是否需要大量跨服務交易」「資料相依性」來檢視 |
| **資料隔離** | 每個服務有自己的資料，不共用資料庫；需要別人的資料時透過 API 或複製 |
| **API 層** | 位於使用者介面與服務之間，可做驗證、路由、監控 |
| **運維重用** | 不重用業務程式碼，用**邊車（sidecar）**模式把監控、日誌、服務發現等運維關注點集中，由獨立的元件提供，讓各服務一致 |
| **編排 vs 協作** | **協作（choreography）**：服務間透過事件互相反應，無中央控制；**編排（orchestration）**：由一個調停者協調。書中提到微服務常使用協作，部分原因是為了保持耦合最低 |
| **交易與傳奇（saga）** | 跨服務的交易要靠**補償**：一個部分失敗，就通知先前成功的部分撤銷。實作複雜，因此書中建議**謹慎使用**，如果發現需要大量跨服務交易，常是粒度劃分有問題的訊號 |

**特性：** 在**可擴展性、彈性、可演進性、可部署性、可測試性**上評價高；**效能**常是問題（網路呼叫多、每個端點都要做安全檢查），可用資料快取與複製等方式提升。成本與運維複雜度高，依賴成熟的自動化（容器、CI/CD、監控）。量子數量多。

## 選擇適當的風格

### 決策依據

選擇風格不是看流行，而是看：

| 考量 | 說明 |
| --- | --- |
| 領域 | 問題的形狀。工作流程導向？資料處理管線？需要客製化？ |
| 架構特性 | 優先的**少數**特性（可擴展性？可部署性？成本？） |
| 資料 | 資料是否共用、是否需要強一致 |
| 組織 | 團隊結構、團隊技能、預算、時程 |
| 單體 vs 分散式 | 是否真的需要多個量子 |

### 架構「時尚」

書中提醒：風格的流行有週期（從分層、SOA 到微服務），不要因為「大家都用」而選。**微服務並非預設答案**：除非確實需要它帶來的能力，否則成本與複雜度可能不值得。

### 兩個案例的選擇

| 案例 | 結果 |
| --- | --- |
| **Silicon Sandwiches**（三明治店線上訂購系統） | 分析架構特性後，只需要一個量子，又是預算不大的簡單應用，所以判斷**單體**即可。書中針對同一個系統做了兩種元件設計：**領域分割**的**模組化單體**（單一資料庫，以領域為中心的元件，如下單、配送、庫存管理、食譜、地點），與技術分割的版本。因為「客製化」是重要特性，另提出**微核心**備案：領域元件與資料庫組成核心，客製化放外掛，並用前端專屬後端（BFF）配接器對應 iOS、Android、網站 |
| **繼續、繼續、成交（Going, Going, Gone）**（線上拍賣） | 可用性、可擴展性、彈性、效能要求高，且各部分要求不同，因此選擇**分散式**。書中比較後認為微服務對「不同部分有不同特性」支援較好，純事件驅動架構則因這些運維特性的考量通常不適合；最終用**微服務**實作，分析結果是 **5 個量子**。服務之間用訊息佇列緩衝（例如出價與拍賣人記錄、出價追蹤），因為速率差異很大 |

書中對服務間通訊的建議：**預設使用同步**，只在必要時使用非同步。因為同步的設計、實作、除錯都比較簡單；非同步在效能與規模上有優勢，但會引入資料同步、死結、競爭條件、除錯困難等問題。

### 風格選擇速查

| 如果你的重點是…… | 考慮 |
| --- | --- |
| 最簡單、最便宜、時程緊 | 分層（或模組化單體） |
| 資料轉換流程 | 管道 |
| 大量客製化、可擴充產品 | 微核心 |
| 要分散式又想控制成本與複雜度 | 服務式 |
| 高效能、高吞吐、非同步 | 事件驅動 |
| 極高並行與彈性、資料庫成為瓶頸 | 空間式 |
| 極端的可部署性、可演進性、獨立擴展，且有成熟的 DevOps | 微服務 |
