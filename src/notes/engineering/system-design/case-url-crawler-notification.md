# 案例：短網址、網路爬蟲、通知系統

> 對應《系統設計面試指南》第 8–10 章。三題的共通點：先估算規模，再把系統拆成「入口、佇列、處理、儲存」幾段，最後談可靠性與擴展。

## 短網址生成器

### 需求與估算

要做的事：給長網址，產生短網址；點短網址，重定向到原網址。書中的假設：

| 項目 | 假設／算式 |
| --- | --- |
| 寫入 | 每天 1 億個網址 → 1 億 / 24 / 3,600 ≈ **1,160 次寫入／秒** |
| 讀寫比 | 10:1 → 約 **11,600 次讀取／秒** |
| 保存期 | 10 年 → 1 億 × 365 × 10 = **3,650 億筆** |
| 單筆大小 | 平均長網址 100 bytes → 約 **36.5 TB** |
| 字元 | `0-9`、`a-z`、`A-Z`，共 62 種 |
| 刪除／更新 | 不支援（簡化） |

### API

| 用途 | 請求 | 回應 |
| --- | --- | --- |
| 縮短 | `POST api/v1/data/shorten`，參數 `{longUrl}` | 短網址 |
| 重定向 | `GET api/v1/{shortUrl}` | 長網址，做 HTTP 重定向 |

### 301 vs 302

| | 301（永久） | 302（暫時） |
| --- | --- | --- |
| 瀏覽器行為 | 快取回應，之後直接去長網址，不再經過短網址服務 | 每次都先到短網址服務，再被導向長網址 |
| 好處 | 降低伺服器負載 | 能追蹤點擊率、來源，適合做分析 |

要降低負載選 301；要做分析選 302。

### 短碼要幾位

找最小的 n 使 `62^n ≥ 3,650 億`：

| n | 62^n |
| --- | --- |
| 5 | 916,132,832 |
| 6 | 56,800,235,584 |
| **7** | **3,521,614,606,208（約 3.5 兆）** |

n = 7 的 **Base62 編碼空間**足以容納需求筆數，但不代表任何 ID 生成方式都只需 7 碼。若要求固定 7 碼，ID 必須保持在 `0 ≤ id < 62^7`，並對較短的結果補前導 `0`；可用集中序號或協調分配的號段避免重複。

**Snowflake 的限制（補充）：** 它把時間戳與節點資訊編進 ID，數值不等於已發出的筆數。本筆記的 Snowflake 範例產生 `1724551110456389632`，轉成 Base62 是 `23osFoACeuQ`（11 碼）。若選用 Snowflake，就要接受較長短碼；不能截斷來維持 7 碼，否則會失去唯一性。

### 兩種產生短碼的做法

| | 雜湊 + 衝突解決 | Base 62 轉換 |
| --- | --- | --- |
| 做法 | 書中示範取雜湊字串前 7 碼，碰撞時附加字串再雜湊；但須另檢查編碼空間是否足夠，見下方限制 | 先由**唯一 ID 生成器**產生 ID，再轉成 62 進位 |
| 長度 | 固定 | 不固定，隨 ID 增加變長 |
| 需要 ID 生成器 | 不需要 | 需要 |
| 衝突 | 可能，需要查資料庫（可用 Bloom 篩選器加速） | 不可能，因為 ID 唯一 |
| 可預測性 | 不可預測下一個 | **ID 遞增時下一個短網址可被猜到**，有安全疑慮 |

**原書方案的容量限制（補充）：** CRC32 的十六進位表示為 8 碼；截取十六進位字串前 7 碼只有 `16^7 = 268,435,456` 種，無法容納 3,650 億筆不同映射，重試也無法增加容量。完整 CRC32 也僅有 `2^32` 種值，即使轉成 Base62 仍不足。若採雜湊方案，須選擇足夠大的輸出空間與適當編碼，並用資料庫唯一約束及重試處理碰撞；**雜湊在截短前就可能碰撞**。

書中選擇 **Base 62 轉換**。轉換例：`11157` 以 62 進位表示是 `2TX`。

```text
11157 = 2 × 62² + 55 × 62 + 59        對應字元：2, T, X
        (0-9 → 0-9；10-35 → a-z；36-61 → A-Z，所以 55 → T、59 → X)
```

書中完整範例：ID `2009215674938` 轉成短碼 `zn9edcu`。

```java
public class Base62Demo {
    static final String ALPHABET =
            "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

    static String toBase62(long n) {
        if (n == 0) return "0";
        StringBuilder sb = new StringBuilder();
        while (n > 0) {
            sb.append(ALPHABET.charAt((int) (n % 62)));
            n /= 62;
        }
        return sb.reverse().toString();
    }

    public static void main(String[] args) {
        System.out.println(toBase62(11157));          // 2TX
        System.out.println(toBase62(2009215674938L)); // zn9edcu
    }
}
```

### 流程

**縮短流程：**

1. 輸入 `longURL`。
2. 查資料庫是否已有，有就直接回傳已存在的短網址。
3. 沒有則由**唯一 ID 生成器**產生 ID；固定 7 碼版本採受控範圍的序號或號段，若改用 Snowflake 則放寬短碼長度。
4. 轉成 Base 62 得到 `shortURL`；固定 7 碼版本補前導 `0`，不截斷。
5. 存入資料庫：`id`、`shortURL`、`longURL`。

**重定向流程：** 讀取多於寫入，所以把 `<shortURL, longURL>` 放快取。使用者點擊 → 負載平衡器 → Web 伺服器 → 查快取 → 沒有就查資料庫（資料庫也沒有就是無效短網址）→ 回傳長網址。

資料模型：先用記憶體雜湊表當起點，但容量有限、成本高，實際上改存**關聯式資料庫**，表有三欄：`id`、`shortURL`、`longURL`。

### 可以接著聊

- **限流**：惡意使用者可能大量送出縮短請求，可依 IP 等規則擋（見「基礎元件」）。
- **Web 層擴展**：無狀態，可直接加減伺服器。
- **資料庫擴展**：複寫與分片。
- **分析**：點擊次數、時間等。

## 網路爬蟲

### 用途與需求

網路爬蟲（web crawler）從種子網址開始下載網頁，抽出其中的連結，再把新連結加入待下載清單，一直重複。用途：搜尋引擎索引、網頁歸檔、資料探勘、監控版權侵權。書中假設：

| 項目 | 假設／算式 |
| --- | --- |
| 目的 | 為搜尋引擎建立索引 |
| 規模 | 每月 10 億頁 → 約 **400 QPS**，峰值約 800 |
| 內容 | 只抓 HTML；新增與編輯過的頁面都要處理；內容重複的頁面要忽略 |
| 儲存 | 平均 500 KB／頁 → **500 TB／月**；保存 5 年 → 約 **30 PB** |

要具備的特性：**可擴展**、**穩健**（對付壞 HTML、無回應的伺服器、惡意連結）、**禮貌**（不在短時間內對同一網站送太多請求）、**可延伸**（容易支援新內容類型）。

### 高階元件

| 元件 | 角色 |
| --- | --- |
| 種子網址 | 起點。大範圍可依地區或主題劃分選擇 |
| **網址邊境（URL Frontier）** | 保存「待下載」網址，類似 FIFO 佇列，並處理禮貌性、優先順序、新鮮度 |
| HTML 下載器 | 從網際網路下載網頁 |
| DNS 解析器 | 把網址轉成 IP |
| 內容解析器 | 解析並驗證頁面；格式錯誤的頁面浪費空間，所以獨立成另一台伺服器，避免拖慢爬取 |
| **看過的內容？** | 比對頁面雜湊，避免重複儲存（約 29% 頁面是重複內容） |
| 內容儲存 | 大部分在磁碟，熱門內容放記憶體 |
| 網址鏈結提取器 | 抽出連結並把相對路徑轉成絕對網址 |
| 網址篩選器 | 排除特定內容類型、副檔名、錯誤連結與黑名單 |
| **看過的網址？** | 追蹤已造訪或已在邊境的網址，避免重複與無限迴圈，常用 Bloom 篩選器或雜湊表 |
| 網址儲存 | 保存已造訪網址 |

**11 步流程**：種子加入邊境 → 下載器取網址 → 向 DNS 取 IP 並下載 → 內容解析 → 傳給「看過的內容？」→ 若是已看過就丟棄，否則傳給提取器 → 抽出連結 → 篩選 → 傳給「看過的網址？」→ 已處理過就不再動作 → 新網址加入邊境。

### 深入設計

**BFS，不是 DFS。** 網路可視為有向圖，深度可能非常深，所以爬蟲通常用 BFS 配 FIFO 佇列。但單純 BFS 有兩個問題：

- 同一頁面的連結大多指回同一主機，會對該主機造成大量平行請求，很不禮貌。
- 沒有優先順序：頁面品質並不相同。

**網址邊境**用來解決：

| 面向 | 做法 |
| --- | --- |
| **禮貌性** | 佇列路由器依**對應表**（主機 → 佇列）決定網址進哪個佇列；每個佇列只含同一主機網址；每個 worker 只從自己的佇列取網址，一次只下載同主機一個頁面，並可加延遲 |
| **優先順序** | 優先順序排序器依 PageRank、網站流量、更新頻率算分數；不同優先順序的佇列，高優先的被選中機率更高 |
| **新鮮度** | 依更新歷史決定是否重爬；重要頁面優先且更頻繁重爬 |
| **儲存** | 網址可能數億個，全放記憶體不持久也不可擴展，全放磁碟太慢，所以採混合：大部分在磁碟，記憶體留 buffer 做 enqueue／dequeue，並定期寫回磁碟 |

**HTML 下載器的最佳化：**

| 項目 | 說明 |
| --- | --- |
| `robots.txt` | 爬取前先檢查並**快取**，說明哪些頁面不可抓 |
| 分散式爬取 | 網址空間切成小部分，各下載器負責一個子集 |
| DNS 快取 | DNS 回應可能要 10–200 ms，且同步介面會阻塞其他執行緒，自己維護對應表並用 cron 更新 |
| 地理位置 | 爬蟲伺服器放在靠近網站主機的地方 |
| 逾時 | 設定最長等待時間，沒回應就換下一頁 |

**穩健性：** 用一致性雜湊分配下載器、保存爬取狀態與資料以便中斷後繼續、妥善處理例外、驗證資料。

**可延伸：** 插入新模組即可，例如 PNG 下載器、Web 監控模組。

**避開有問題的內容：**

| 問題 | 做法 |
| --- | --- |
| 重複內容 | 雜湊或 checksum |
| **蜘蛛陷阱**（無限深度目錄，如 `/foo/bar/foo/bar/...`） | 設定網址長度上限；沒有萬用解法，可人工識別並排除或套用自訂篩選器 |
| 資料雜訊（廣告、垃圾郵件網址、無價值內容） | 盡可能排除 |

### 可以接著聊

- **伺服端渲染**：許多網站用 JavaScript 動態產生連結，直接下載解析抓不到，需先渲染。
- 用**反垃圾**做法篩掉低品質頁面。
- 資料層的複寫、分片，以及無狀態的水平擴展。
- 分析資料用於微調。

## 通知系統

### 需求

通知有三種：**手機推送**、**簡訊（SMS）**、**電子郵件**。書中的假設：

- 軟（soft）即時：盡快送達，負載大時稍有延遲可接受。
- 支援 iOS、Android、筆記型／桌上型電腦。
- 觸發來源：客戶端應用程式，或伺服端排程。
- 使用者可選擇停止接收（opt-out）。
- 每天 1,000 萬則推送、100 萬則簡訊、500 萬封電子郵件。

### 三種通道的第三方服務

| 通道 | 流程 |
| --- | --- |
| iOS 推送 | Provider（提供裝置 token 與 JSON payload）→ **APNs** → iOS 設備 |
| Android 推送 | Provider → **FCM** → Android 設備 |
| SMS | Provider → 第三方 SMS 服務（Twilio、Nexmo 等）→ 手機 |
| Email | Provider → 商用郵件服務（Sendgrid、Mailchimp 等）→ 信箱 |

### 從初始設計到改進

初始設計把通知服務放在**單一伺服器**，有三個問題：**單點故障**、**難以擴展**（資料庫、快取與通知處理全綁在一起）、**效能瓶頸**（建構 HTML、等待第三方回應很耗時）。

改進做法：資料庫與快取移出通知伺服器；加通知伺服器並可自動水平擴展；**每種通知類型各自一個訊息佇列**，某個第三方服務出問題不會影響其他類型。

```text
各服務 → 通知伺服器（驗證、限流、查快取／資料庫、建構事件）
          → iOS 佇列 / Android 佇列 / SMS 佇列 / Email 佇列
          → 各自的 worker → 第三方服務 → 使用者設備
```

流程：服務呼叫通知伺服器 API → 伺服器查使用者資訊、設備 token、通知設定 → 事件進對應佇列 → worker 取出事件 → 送給第三方服務 → 送達設備。

### 可靠性與其他功能

| 主題 | 做法 |
| --- | --- |
| **不能丟資料** | 通知可以延遲，不能遺失；把通知資料寫入**通知日誌資料庫**，並實作**重試** |
| **只會收到一次嗎？** | 不能保證。分散式系統可能重複。以**事件 ID 去重**：看過就丟棄，否則發送。書中引用文章：無法保證 exactly-once |
| 通知範本 | 預先格式化，參數化名稱、日期、連結，格式一致且減少錯誤 |
| 通知設定 | 資料表如 `user_id`、`channel`、`opt_in`；送出前先檢查 |
| 限流 | 限制使用者每天收到的數量，避免太多後被整個關掉 |
| 重試 | 第三方失敗時放回佇列重試；問題持續就警示開發者 |
| 推送安全 | `appKey`／`appSecret` 驗證，只有通過驗證的客戶端能呼叫 |
| 監控 | 最關鍵：**佇列裡的通知總數**，太多代表 worker 跟不上，要加 worker |
| 事件追蹤 | 開啟率、點擊率、參與度，整合分析服務 |

最後設計新增：通知伺服器的驗證與限流、重試機制、範本、監控與追蹤。
