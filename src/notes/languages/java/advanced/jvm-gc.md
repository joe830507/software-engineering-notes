# 垃圾回收

## 如何判斷物件可以被回收

**引用計數法**：每被參考一次就加一，計數為 0 就回收。實作簡單，但**無法處理循環參考**（A 參考 B、B 參考 A），所以 Java 不用。

**可達性分析**（Java 採用）：從一組 **GC Roots** 出發往下走，走不到的物件就可回收。

GC Roots 包含：

- 執行緒堆疊中的區域變數和參數
- 類別的靜態欄位
- 常數池中的參考
- JNI 參考
- 存活的執行緒本身
- 被 `synchronized` 持有的物件

## 強、軟、弱、虛參考

| 參考 | 何時被回收 | 用途 |
| --- | --- | --- |
| 強參考 | 只要還有強參考就不會回收 | 一般的 `Object o = new Object()` |
| 軟參考 `SoftReference` | 記憶體不足、即將 OOM 之前 | 記憶體敏感的快取 |
| 弱參考 `WeakReference` | 下一次 GC 就回收 | `WeakHashMap`、`ThreadLocalMap` 的 key、避免監聽者造成洩漏 |
| 虛參考 `PhantomReference` | 隨時，`get()` 永遠回傳 null | 搭配 `ReferenceQueue` 追蹤物件被回收的時間點，做資源清理（`Cleaner`） |

## 垃圾回收演算法

| 演算法 | 做法 | 優點 | 缺點 |
| --- | --- | --- | --- |
| 標記-清除 | 標記存活物件，清除其餘 | 簡單 | 產生記憶體碎片 |
| 複製 | 把存活物件複製到另一塊空間，整塊清掉原空間 | 沒有碎片、速度快 | 浪費一半空間；存活物件多時複製成本高 |
| 標記-整理 | 標記後把存活物件往一端移動 | 沒有碎片、不浪費空間 | 移動物件的成本高 |
| 分代收集 | 依物件存活時間分區，各用適合的演算法 | 綜合以上優點 | |

**分代假說**：大部分物件「朝生夕死」，活得越久的物件越不容易死。

- **新生代**：分成 Eden 和兩個 Survivor（S0、S1），預設比例 8:1:1。新物件在 Eden 配置；Minor GC 時把 Eden 和其中一個 Survivor 的存活物件複製到另一個 Survivor，年齡加一。存活的少，適合**複製演算法**。
- **老年代**：年齡達到門檻（預設最大 15）的物件晉升到這裡；Survivor 放不下的、大物件也可能直接進入老年代。適合**標記-清除或標記-整理**。

## 常見的垃圾回收器

| 回收器 | 特點 | 適用 |
| --- | --- | --- |
| Serial | 單執行緒、Stop-The-World | 小型應用 |
| Parallel | 多執行緒、目標是吞吐量，**Java 8 預設** | 批次運算、不在意停頓 |
| CMS | 並行標記清除，低停頓；有碎片、浮動垃圾問題 | **Java 9 廢棄、Java 14 移除** |
| **G1** | 把堆積切成許多 Region，優先回收垃圾最多的 Region；可設定停頓目標；**Java 9 起預設** | 大部分伺服器應用 |
| ZGC | 停頓時間在毫秒以下，幾乎不受堆積大小影響；Java 15 正式版；Java 21 推出分代模式，Java 23 起分代為預設 | 大堆積、對延遲非常敏感 |
| Shenandoah | 和 ZGC 類似的低停頓回收器，由 Red Hat 開發 | 同上 |

G1 的重點：

- 堆積分成大小相同的 Region（1～32 MB），每個 Region 動態扮演 Eden、Survivor、Old 或 **Humongous**（存放超過半個 Region 的大物件）。
- `-XX:MaxGCPauseMillis` 設定停頓目標（預設 200 ms），G1 依此決定每次回收多少 Region。
- 回收類型：Young GC、Mixed GC（年輕代加上部分老年代 Region）；回收跟不上時退化成 Full GC，應該要避免。

## Minor GC、Major GC、Full GC

- **Minor GC / Young GC**：只回收新生代，Eden 滿了就觸發，頻繁但快。
- **Major GC**：回收老年代（用語不太統一）。
- **Full GC**：回收整個堆積（加上 Metaspace），停頓最久。

觸發 Full GC 的常見原因：

- 老年代空間不足（大量物件晉升、大物件直接進入老年代）。
- Metaspace 不足。
- 呼叫 `System.gc()`（只是建議，可用 `-XX:+DisableExplicitGC` 停用）。
- G1 的回收速度跟不上配置速度（`to-space exhausted`、Evacuation Failure）。

Full GC 頻繁的排查方向：記憶體洩漏（老年代 GC 後也降不下來）、堆積設太小、一次載入大量資料（例如一個查詢撈了幾百萬筆到記憶體）。

## Stop-The-World 與 Safepoint

**Stop-The-World**：GC 的某些階段需要暫停所有應用程式執行緒，確保物件參考關係不會在分析途中改變。低停頓 GC（G1、ZGC）的目標就是盡量縮短或避免這段時間。

**Safepoint**：執行緒不能在任意指令暫停，必須跑到「安全點」，這時 JVM 知道所有物件參考在哪裡。安全點通常在方法呼叫、迴圈回跳處、例外拋出處。

陷阱：用 `int` 當索引的「可數迴圈」，JIT 為了效能可能不放安全點。如果這個迴圈跑很久，其他執行緒都已經停下來等 GC，只剩它還在跑，整個 JVM 的停頓時間就會被拉長（Time To Safepoint 過長）。
